The previous topic assumed a "vehicle computer" running AAOS as one guest
among several. The dedicated SDV track's own architecture module already
covers *why* zonal wiring replaces functional domains — the harness-weight
numbers, the Ethernet/TSN requirement, the software-fuse angle. This topic
assumes that background and asks the question that module never needs to:
what does this hardware shift actually change for the Android engineer
sitting above VHAL?

<Plain>
In one sentence: zone controllers wire to whatever hardware is physically
nearby regardless of function, forward everything to a small number of
central computers over a backbone network, and the application logic that
used to live on a dedicated per-function ECU moves to run as software on
that central compute — often the very vehicle computer AAOS runs on as one
guest among several.
</Plain>

## What moves, and what stays

The physical sensor and actuator interfaces do not change — a seat motor
still needs a local controller close enough to drive it in real time. What
moves is the **application logic**: "is the seat allowed to move while a
child lock is active" is no longer decided on a dedicated seat ECU, it runs
as software on a central compute node, reachable from any zone controller
over the backbone. This is the precondition for the whole software-defined
vehicle idea in the earlier topics: logic that used to be welded to one piece
of hardware becomes a deployable, updatable service, because it no longer
lives on hardware dedicated to that one function.

```text title="Where a seat-position update travels, roughly"
seat motor position sensor
  → local zone controller (front-left), reads it over a short local bus
  → backbone network (Ethernet) to central compute
  → seat control service (software, not a dedicated ECU) applies logic
  → command sent back down the same path to the seat motor driver
```

<Scenario title="On a real programme">
A supplier delivers a zone controller that is functionally correct in
isolation but adds nine milliseconds of round-trip latency to what used to be
a same-board control loop on the old domain ECU. Nobody notices in unit
testing. It shows up as a barely perceptible lag in seat memory recall — a
feature nobody thought of as latency-sensitive, because on the old
architecture it never had to travel anywhere. Zonal architectures move
control loops that used to be entirely local onto a shared network, and any
function that was implicitly relying on "same board, no meaningful delay"
needs its timing budget re-checked, not assumed.
</Scenario>

## Why this matters for an AAOS engineer specifically

AAOS itself does not care which architecture the vehicle uses — the VHAL
boundary already abstracts "how do I get this value" away from "which ECU
physically owns it," which is exactly what makes the transition possible
without rewriting the app layer. What changes for you is *reliability
expectations*: a zonal architecture means a single central compute failure
can affect functions that used to be isolated on entirely separate ECUs, so
the software layer picks up more of the responsibility for degrading
gracefully — the same responsibility that mixed-criticality virtualization
was designed to contain.

<Callout type="note" title="Zonal is a wiring decision, not a software one">
Nothing about VHAL, Car Service, or the app layer changes based on which E/E
architecture sits underneath. What changes is where latency and failure
domains sit — worth checking explicitly for any feature that assumes a
same-board response time, because that assumption quietly held on the old
architecture and does not automatically hold on the new one.
</Callout>

<Recap>
- Zone controllers wire to whatever hardware is physically nearby and
  forward everything to a small number of central computers — the hardware
  shift the SDV track's own architecture module covers in depth.
- Zonal architecture is what makes a single powerful vehicle computer
  practical — it turns application logic that used to be welded to dedicated
  hardware into a deployable service reachable from any zone.
- VHAL already hides "which physical ECU owns this" from app code, which is
  exactly why the app layer does not need to change when the underlying
  wiring topology does.
- What does change is latency and failure-domain assumptions — control loops
  that used to be same-board now cross a network, and anything relying on
  that used to be free now needs its budget checked.
</Recap>
