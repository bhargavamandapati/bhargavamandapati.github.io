`ux-restrictions` covered the framework's usual mechanism: a driving-state
change tells your activity what it may no longer show, and a
distraction-optimised layout adapts. Parked-only content is a different,
stricter category underneath that one — not "simplified while driving," but
genuinely unavailable while driving, with no distraction-optimised fallback
offered at all, because no fallback was judged safe enough to exist.

<Plain>
Most restricted content has two versions: the full one, and a simplified
one shown while driving. Parked-only content has exactly one version, and
the platform's answer to "what do I show while driving" is nothing —
the activity does not get a reduced layout, it does not get a chance to
degrade gracefully, it simply is not reachable until
`CarDrivingState` reports the vehicle stationary.
</Plain>

## What actually qualifies

The bar is deliberately narrow. Content requiring sustained visual attention,
free-text input, or a decision with real consequences typically qualifies —
setting up a complex navigation route with multiple waypoints, browsing a
long list with no voice-search equivalent, configuring anything with more
than a few taps' worth of options. Content that is merely "nice to simplify"
does not qualify — that is what the ordinary UX-restriction mechanism
already handles, correctly, with a driving-optimised layout rather than a
hard lock.

| Signal | Usually parked-only | Usually driving-optimised instead |
| --- | --- | --- |
| Free-text search with no voice alternative | Yes | — |
| A list with a voice-search or single-tap-select alternative | — | Yes, simplified |
| Multi-step account setup or configuration | Yes | — |
| Glanceable status (battery, next turn, now-playing) | — | Never restricted at all |

<Analogy title="A door that does not open, not a door that opens slower">
An ordinary UX restriction is a door that still opens while the vehicle
moves, just more slowly and with fewer things visible through it. A
parked-only restriction is a door that is genuinely locked — not slowed,
not simplified, not reachable by any interaction at all — until the vehicle
reports stationary. The difference is not degree, it is kind.
</Analogy>

## Why so few apps actually use it

Declaring content parked-only is a one-way commitment with a real cost: the
platform enforces it uniformly, which means a feature a team is confident
is "fine for a glance" does not get to make that argument case by case — it
either qualifies for the strict category or it does not, and the review
bar for "does not" is high. Most teams discover that a distraction-optimised
layout, done properly, satisfies the actual safety requirement for nearly
everything they wanted to build — parked-only ends up reserved for a small,
genuinely irreducible set of interactions, not a default reached for out of
caution.

<Scenario title="On a real programme">
A settings screen for configuring a custom dashboard layout is proposed as
parked-only, on the reasoning that "it's just settings, nobody needs it
while driving." Review pushes back: nothing about choosing which four
gauges appear is inherently more dangerous than any other settings screen
already shipping with a driving-optimised layout, and locking it entirely
removes a legitimate use case — a passenger adjusting it for the driver
mid-trip. The screen ships with a standard UX-restricted layout instead,
and parked-only is reserved for the one part of the flow that genuinely
cannot be simplified: importing a layout from a file, which requires
sustained attention on a file browser with no safe reduced form.
</Scenario>

## What this means for how you build the activity

The actual enforcement mechanism is manifest metadata, not a runtime flag
your layout code inspects. An activity declares itself fit to run while
driving with `<meta-data android:name="distractionOptimized"
android:value="true"/>`; an activity that omits it, or sets it to `false`,
is exactly what "parked-only" means in platform terms. `CarPackageManagerService`
is what checks that declaration against the current driving state before the
activity is allowed to launch or stay in the foreground, swapping in a
blocking activity if the vehicle starts moving while a non-optimised screen
is showing. There is no `CarUxRestrictions` flag to interpret on top of that
— the platform's answer is binary, checked before the activity is even
shown, not a restriction level your layout code branches on. The design work
happens earlier: deciding whether a screen genuinely belongs in this
category at all, because once it does, there is no partial-credit
implementation to reach for.

Templated apps get the same guarantee through a different door: the Car App
Library marks `SignInTemplate` and `LongMessageTemplate` parked-only at the
template level, enforced by the template host rather than by
`CarPackageManagerService` directly — the same binary gate, applied at the
point that fits apps with no full Activity of their own to check.

```text title="Where the decision actually happens"
driving state changes to Parked
  → your parked-only activity's intent filter becomes resolvable
  → the launcher / calling activity can now navigate to it

driving state changes to Moving
  → the activity is not shown a restricted layout —
    it is simply not the destination any navigation can reach
```

<Callout type="warning" title="Test the actual transition, not just each state in isolation">
The failure mode worth checking is a parked-only screen already open when
the vehicle starts moving — confirm it is dismissed or blocked
appropriately rather than left interactive, which is a different bug from
simply never launching it while driving in the first place.
</Callout>

<Recap>
- Parked-only is a stricter, separate category from ordinary UX
  restrictions — no distraction-optimised fallback is offered, because none
  was judged safe enough to exist.
- It qualifies content requiring sustained attention, free-text input, or a
  consequential multi-step decision — not content that is merely
  simplifiable, which the ordinary restriction mechanism already handles.
- Few apps use it because a properly built driving-optimised layout
  satisfies the real safety requirement for almost everything; parked-only
  is reserved for the small remainder that genuinely cannot degrade.
- There is no restriction *level* to branch on in code — the decision is
  made at design time, and the platform enforces it as a binary reachability
  gate, not a layout your activity adapts. The lever is the manifest's
  `distractionOptimized` metadata, checked by `CarPackageManagerService`, not
  a runtime flag your code inspects.
</Recap>
