A phone that hangs gets rebooted by its owner. A head unit that hangs is a safety
and warranty problem, so the platform polices it. CarWatchdog is that policing,
and it has two jobs: liveness and resource discipline.

<Plain>
CarWatchdog exists because a vehicle cannot rely on someone noticing that
something has hung.

It does two quite different jobs:

**Health checks** — services must periodically say they are alive. Stop
answering and you get killed.

**Resource overuse** — apps that write too much to storage get warned, then
throttled, then killed.

The second one surprises people, because on a phone nothing cares how much you
write.
</Plain>

<Analogy title="Like a night watchman">
Someone walks the building on a schedule and expects a response at each station.
Miss a check-in and they come looking, and eventually they raise the alarm.

Separately, they notice that one office is filling the skip every single night —
not an emergency, but not sustainable either, and eventually somebody has a word.
</Analogy>

## Health checks

CarWatchdog pings registered clients. A client that does not answer within its
timeout is considered hung, and the service terminates it.

```kotlin title="Registering as a watchdog client" showLineNumbers
class CriticalService : Service() {

    private lateinit var watchdog: CarWatchdogManager

    private val callback = object : CarWatchdogManager.CarWatchdogClientCallback() {
        override fun onCheckHealthStatus(sessionId: Int, timeout: Int): Boolean {
            // Return true ONLY if you are genuinely healthy right now.
            // Returning true from a hung process defeats the entire mechanism.
            return workerThread.isResponsive()
        }

        override fun onPrepareProcessTermination() {
            // Last chance. Flush anything that must survive. Be quick.
            persistCriticalState()
        }
    }

    override fun onCreate() {
        watchdog = car.getCarManager(Car.CAR_WATCHDOG_SERVICE) as CarWatchdogManager
        watchdog.registerClient(
            mainExecutor, callback, CarWatchdogManager.TIMEOUT_MODERATE,
        )
    }
}
```

Three timeout tiers, chosen by how quickly your failure matters:

| Timeout | Order of magnitude | For |
| --- | --- | --- |
| `TIMEOUT_CRITICAL` | ~3 s | Safety-adjacent services |
| `TIMEOUT_MODERATE` | ~5 s | Most system services |
| `TIMEOUT_NORMAL` | ~10 s | Background work |

<Callout type="warning" title="Never answer the health check from the main thread only">
The classic mistake is `onCheckHealthStatus` returning `true` unconditionally
because it is called on a healthy binder thread while your actual worker thread is
deadlocked. Check the thing that can hang, not the thing doing the checking.
</Callout>

<Callout type="note" title="The kill signal is SIGSYS, not SIGKILL">
A client that misses its deadline is ended with `SIGSYS`, not `SIGKILL` —
deliberately, since `SIGSYS` can be caught by a signal handler, giving
`debuggerd`/`tombstoned` a chance to write a full backtrace before the process
actually dies. `onPrepareProcessTermination()` runs on the same executor as
`onCheckHealthStatus()`, so in rare cases it can be delayed, or never get a
chance to run, if that thread is still the one that's hung. Give the two
callbacks separate executors if the termination warning matters to you.
</Callout>

## Resource overuse

The second job is I/O. Flash storage in a vehicle has a finite write budget and
must survive fifteen years. An app writing continuously will exhaust it long
before that, so CarWatchdog enforces per-app write quotas.

```xml title="Declaring an I/O budget (system app resource overuse config)"
<resourceOveruseConfiguration version="1.0">
  <componentType>THIRD_PARTY</componentType>
  <ioOveruseConfiguration>
    <componentLevelThresholds>
      <thresholds>
        <name>THIRD_PARTY</name>
        <backgroundModeBytes>1048576</backgroundModeBytes>     <!-- 1 MiB/day -->
        <foregroundModeBytes>10485760</foregroundModeBytes>    <!-- 10 MiB/day -->
        <garageModeBytes>52428800</garageModeBytes>            <!-- 50 MiB -->
      </thresholds>
    </componentLevelThresholds>
  </ioOveruseConfiguration>
</resourceOveruseConfiguration>
```

Note `garageModeBytes` is far larger. That is the design intent: **bulk writing
belongs in Garage Mode**, when the vehicle is parked, not while someone is
driving.

```kotlin title="Knowing before you are killed"
watchdog.addResourceOveruseListener(
    mainExecutor,
    CarWatchdogManager.FLAG_RESOURCE_OVERUSE_IO,
) { stats ->
    val io = stats.ioOveruseStats ?: return@addResourceOveruseListener
    if (io.remainingWriteBytes < LOW_WATERMARK) {
        // Back off: batch writes, drop caching, defer to Garage Mode.
        enterFrugalMode()
    }
}
```

<Callout type="warning" title="A stale killable flag in the listener's own stats">
Marking a package non-killable (via the shell's
`watchdog-control-package-killable-state`, or the equivalent system API)
genuinely blocks a manual overuse kill — the enforcement path checks a
correctly-updated record. But that same package's own
`IoOveruseStats.isKillableOnOveruse()`, as delivered through this listener, can
keep reporting the old value for tens of seconds afterward: the kill path and
the listener-facing snapshot are backed by two separate internal caches that
do not reconcile immediately. Do not treat the listener's killable flag as
live — query the authoritative killable-state API if a decision depends on it.
</Callout>

```bash title="Checking your own consumption"
adb shell dumpsys car_service --services CarWatchdogService
```

Run this after a soak test. Teams are routinely surprised — a logging library
writing a few kilobytes per second is 300 MB a day.

<Callout type="note" title="Boot-time writes may not trip onOveruse() right away">
I/O accounting runs in distinct collection phases with different intervals:
short boot-time, wake-up and user-switch windows near those events, and a
periodic window (around 60 seconds in steady state) otherwise. A write
recorded during one of the short, event-driven windows is captured in the byte
count but does not reliably trigger `onOveruse()` immediately — the callback
fires once a later periodic collection picks it up. If a listener seems to
miss an overuse right after boot, check again once the system has settled
into steady-state periodic collection.
</Callout>

<Callout type="note" title="The watchdog daemon also fronts real-time thread scheduling, via a separate manager">
Beyond health checks and I/O overuse, the same native `carwatchdogd` process
backs a third, less obvious capability: `CarPerformanceManager.setThreadPriority()`
lets a `signature|privileged` app ask the Linux kernel directly for real-time
scheduling (`SCHED_FIFO`/`SCHED_RR`) on one of its own threads — a genuine
`sched_setscheduler()` call, not a Car-Service abstraction over it, with an
out-of-range priority rejected client-side before it reaches the daemon. A
sibling API on the same manager, `addCpuAvailabilityChangeListener()`, is
real in the SDK but throws `UnsupportedOperationException` — it was never
implemented, and the permission its own annotation names isn't declared
anywhere as a real `<permission>` either, so a manifest entry for it is
inert. Check what a "genuinely real vs. still unimplemented" API actually
does before building against it, even when both live on the same class.
</Callout>

## Writing less

The patterns that keep you inside budget:

**Batch.** Accumulate in memory and write once, rather than per event. One write
of 100 records instead of 100 writes.

**Do not log to disk in production.** Verbose logging is the most common cause of
overuse. Log to logcat, which is a ring buffer in memory, not to files.

**Use Garage Mode.** Any bulk sync, cache warm or database compaction belongs in
a `JobScheduler` job with idle constraints.

**Avoid write amplification.** Rewriting a whole file to change one field, or a
database without batched transactions, multiplies real flash writes far beyond
what your code appears to do.

```kotlin title="Batching, concretely"
// Bad: a write per event
fun onSignal(v: Reading) = dao.insert(v)

// Good: one transaction per window
private val pending = ArrayDeque<Reading>()
fun onSignal(v: Reading) {
    pending += v
    if (pending.size >= 200) flush()
}
private fun flush() = db.runInTransaction {
    dao.insertAll(pending.toList()); pending.clear()
}
```

## What termination looks like
<Scenario title="Why your app was killed overnight">
A telemetry component buffers events to disk, flushing every few seconds. It runs
fine for a week, then users report it disappearing.

CarWatchdog killed it for **I/O overuse**. Flash in a vehicle has a finite write
endurance and a fifteen-year service life, so sustained writes are treated as a
real problem rather than a performance detail.

What to do instead:

- **Batch aggressively.** One write a minute rather than twenty a second.
- **Keep buffers in memory** and flush on a schedule or at shutdown, not per
  event.
- **Aggregate before writing.** A count is smaller than the events it counts.
- **Check your quota** in `dumpsys car_service --services CarWatchdogService`
  rather than guessing.

The warning arrives before the kill, in the logs. Nobody reads it, which is why
the first symptom is usually the termination.
</Scenario>


An app killed for overuse is not just stopped — it may be prevented from
restarting until the next daily window, and repeated offenders can be disabled
entirely. From the driver's perspective the app simply stopped working, with no
explanation.

```bash title="Was I killed, and why?"
adb logcat -b all | grep -iE 'CarWatchdog|resource overuse|killed'
adb shell dumpsys car_service --services CarWatchdogService | grep -A20 -i overuse
```

<Callout type="tip" title="Test against the budget, not against your laptop">
Run a realistic session with `dumpsys car_service --services CarWatchdogService`
before and after and compare written bytes. A feature that looks free on a
development machine with fast NVMe can be the top consumer on the target.
</Callout>

<Recap>
- CarWatchdog does two jobs: **liveness checks** on services and **resource
  overuse** monitoring on apps.
- Services must respond to health pings; failing to answer gets the process
  killed.
- **I/O overuse is real** — flash endurance over a fifteen-year life makes
  sustained writes a genuine constraint.
- Warnings arrive in the log before termination, and are almost always missed.
- Batch and aggregate writes; keep buffers in memory and flush on a schedule.
- `dumpsys car_service --services CarWatchdogService` shows your quota and
  current usage — check it rather than guessing.
</Recap>
