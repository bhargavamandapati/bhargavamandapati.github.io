The most common question from an app team new to AAOS is "can I get X?" This page
is the map that answers it.

<Plain>
`android.car` is the entire public surface of the vehicle for an app. One entry
point, `Car`, hands out managers, and each manager owns one area.

The practical skill is not memorising them. It is knowing **what you are allowed
to reach** from an ordinary app, what needs privilege, and how to find out at
runtime rather than assuming.
</Plain>

<Analogy title="Like a switchboard">
There is one number to call, and the operator connects you to a department. Some
departments will talk to anyone. Some need you to be staff. A few do not exist in
this building at all.

Asking the operator is always better than guessing an extension.
</Analogy>

## Everything starts at `Car`

```kotlin title="The entry point"
val car = Car.createCar(context)

val properties = car.getCarManager(Car.PROPERTY_SERVICE) as CarPropertyManager
val audio      = car.getCarManager(Car.AUDIO_SERVICE) as CarAudioManager
val restrict   = car.getCarManager(Car.CAR_UX_RESTRICTION_SERVICE)
        as CarUxRestrictionsManager
```

`Car` is a connection to Car Service, and the managers are handles into its
subservices. Read the constants in <Src path="packages/services/Car/car-lib/src/android/car/Car.java" label="Car.java" /> —
it is the authoritative list of what exists on your platform version.

## The managers worth knowing

| Manager | What it gives you | Typical permission |
| --- | --- | --- |
| `CarPropertyManager` | All vehicle properties | Per property |
| `CarAudioManager` | Zones, volume groups, focus | `CAR_CONTROL_AUDIO_VOLUME` |
| `CarUxRestrictionsManager` | Driver distraction state | none to read |
| `CarPackageManager` | Is this activity distraction-optimised? | none to read |
| `CarPowerManager` | Power state, shutdown callbacks | `CAR_POWER` |
| `CarUserManager` | User switching and lifecycle | `MANAGE_USERS` |
| `CarOccupantZoneManager` | Displays, seats, users | varies |
| `CarWatchdogManager` | Health reporting | none to register |
| `CarInfoManager` | Static vehicle info (make, model, year) | `CAR_INFO` |
| `CarSensorManager` | Legacy sensor wrapper — prefer properties | varies |
| `CarNavigationStatusManager` | Push turn-by-turn to the cluster | `CAR_NAVIGATION_MANAGER` |
| `CarAppFocusManager` | Exclusive ownership of navigation or voice-command | none to request |

## Permissions, and the two-tier reality

Car permissions split into two very different groups, and confusing them wastes
weeks.

**Normal/dangerous permissions** any app can request, subject to user consent:

```xml title="Requestable by a normal app"
<uses-permission android:name="android.car.permission.CAR_INFO"/>
<uses-permission android:name="android.car.permission.CAR_ENERGY"/>
<uses-permission android:name="android.car.permission.CAR_SPEED"/>
<uses-permission android:name="android.car.permission.CAR_EXTERIOR_ENVIRONMENT"/>
```

**Signature/privileged permissions** that require the platform key or a
`privapp-permissions` grant:

```xml title="System apps only"
<uses-permission android:name="android.car.permission.CONTROL_CAR_CLIMATE"/>
<uses-permission android:name="android.car.permission.CONTROL_CAR_DOORS"/>
<uses-permission android:name="android.car.permission.CONTROL_CAR_SEATS"/>
<uses-permission android:name="android.car.permission.CAR_POWER"/>
```

<Callout type="warning" title="Anything that actuates the vehicle is signature-level">
Reading speed is a normal permission. Moving a window is not. If your feature
writes a property that physically moves something, your app must be part of the
system image — which means the OEM ships it, and your release cadence becomes
theirs. Find this out during scoping, not during integration.
</Callout>

<Callout type="note" title="Four legacy managers are the exact same service under different names">
`CarCabinManager`, `CarSensorManager`, `CarInfoManager` and
`CarVendorExtensionManager` all resolve, through `Car.getCarManager()`'s own
service-name dispatch, to the identical `CarPropertyService` binder object
`CarPropertyManager` uses — not a separate implementation kept loosely in
sync, one live store with several typed views onto it. A write through any
one of them is visible instantly through any other, with no polling delay
and no translation step, confirmed both directions on a real property. Old
code still targeting a `@Deprecated` manager from this group is reading and
writing the platform's real, current state, not a frozen legacy snapshot —
there's no correctness reason to migrate it, only a documentation one.
</Callout>

<Callout type="note" title="CarAppFocusManager arbitrates two things only, and foreground wins">
Exactly two focus types exist — `APP_FOCUS_TYPE_NAVIGATION` and
`APP_FOCUS_TYPE_VOICE_COMMAND` — each with one owner at a time, system-wide.
A foreground owner can only be displaced by another foreground requester (or
a caller holding `CAR_DISPLAY_IN_CLUSTER`, an exception meant for cluster
navigation renderers); a request from a background component fails outright
against a foreground owner, and the loser's still-running process gets a
real `onAppFocusOwnershipLost()` callback the instant it's displaced, not a
silent state change. Note that "foreground" here is Activity-visibility-specific
(`isInForeground`) — a plain `startService()`-launched background service
doesn't qualify even if it's doing active work, and a cold app needs
`am start-foreground-service` rather than `start-service` just to launch at
all, since Android's own background-service-start restriction blocks the
latter unconditionally.
</Callout>

## Deciding whether something is possible

A reliable four-step check, in order:

**1. Does a system property already exist for it?**
Search <Src path="packages/services/Car/car-lib/src/android/car/VehiclePropertyIds.java" label="VehiclePropertyIds.java" />.
If yes, you inherit the permission mapping and CTS coverage.

**2. Does this vehicle actually implement it?**
A property existing in AOSP says nothing about this trim.

```bash
adb shell dumpsys car_service --services CarPropertyService | grep -i window
```

**3. What permission does it need, and can you hold it?**
If it is signature-level and you are not in the system image, the answer is no
until the OEM includes you.

**4. Is it restricted while driving?**
Even with access, `CarUxRestrictionsManager` may block the interaction above a
speed threshold.

## Feature detection, not assumption
<Scenario title="Why the same APK behaves differently in two vehicles">
An app calls `CarPropertyManager.getProperty(HVAC_SEAT_TEMPERATURE, ...)` and
works fine in one vehicle, throws in another.

Nothing is broken. The second vehicle simply does not have heated seats, so the
property is not in its config.

This is normal and permanent: **the same APK runs across a range of vehicles with
different hardware**. The correct pattern is to ask rather than assume:

1. `getPropertyList()` or `isPropertyAvailable()` before using a property.
2. Hide UI for features the vehicle does not have — do not show a disabled
   control the driver can never use.
3. Treat absence as a normal state, not an error worth logging loudly.

The same applies to whole managers: a `Car.getCarManager` call can return null
for a subsystem this build does not include.
</Scenario>


Different vehicles, trims and platform versions expose different things. Ask:

```kotlin title="Detect, do not assume"
// Is this an automotive build at all?
val isCar = context.packageManager
    .hasSystemFeature(PackageManager.FEATURE_AUTOMOTIVE)

// Does this vehicle support the property, in this area?
val supported = properties.propertyList.any {
    it.propertyId == VehiclePropertyIds.WINDOW_POS
}

// Is it available right now? (trailer absent, module asleep, …)
val available = properties.isPropertyAvailable(
    VehiclePropertyIds.WINDOW_POS, VehicleAreaWindow.WINDOW_ROW_1_LEFT,
)
```

Every one of those can differ between two cars rolling off the same line with
different option packages.

## The distraction rules apply to you

```kotlin title="Responding to UX restrictions"
val manager = car.getCarManager(Car.CAR_UX_RESTRICTION_SERVICE)
        as CarUxRestrictionsManager

manager.registerListener { restrictions ->
    val noVideo = restrictions.isRequiresDistractionOptimization &&
        (restrictions.activeRestrictions and
            CarUxRestrictions.UX_RESTRICTIONS_NO_VIDEO) != 0

    if (noVideo) pauseVideoPlayback()
}
```

The restriction set includes limits on video, keyboard entry, string length and
the number of items in a list. They change with driving state, and the framework
enforces the important ones whether you cooperate or not — cooperating just makes
the experience less jarring.

<Recap>
- `Car` is the single entry point; every capability arrives as a manager from it.
- The managers worth knowing first are property, audio, power, UX restrictions,
  occupant zone and watchdog.
- Permissions are **two-tier**: normal ones any app can request, and
  signature/privileged ones that need platform signing plus allowlisting.
- **Detect features, never assume them** — the same APK runs on vehicles with
  different hardware, and absence is normal.
- A manager itself can be null if the build does not include that subsystem.
- **UX restrictions apply to you**, not just to the launcher; check them before
  showing anything complex while driving.
</Recap>
