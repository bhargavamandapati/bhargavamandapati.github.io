A phone has one screen and one user. A modern cockpit has a centre display, a
cluster, a passenger screen and two rear entertainment screens — with different
people using them simultaneously.

`CarOccupantZoneService` is how the platform stops pretending otherwise.

<Plain>
An occupant zone is the platform's answer to a question a phone never asks:
**who is this screen for?**

A zone ties together a seat, one or more displays, and a user. That lets the
system know that the rear-left screen belongs to a passenger, not the driver —
which changes what may be shown on it and who owns it.
</Plain>

<Analogy title="Like seats in a cinema">
A ticket is not just admission to the building; it names a seat. The seat
determines which screen you can see and which armrest is yours.

Occupant zones do the same job: they turn "a display" into "the display in front
of the person in seat 2, who is signed in as this user".
</Analogy>

## The model

An **occupant zone** is a seat position that can have a user and one or more
displays.

```text title="A three-screen cockpit"
Zone: DRIVER          seat ROW_1_LEFT
   ├─ DISPLAY_TYPE_MAIN         centre stack
   ├─ DISPLAY_TYPE_INSTRUMENT_CLUSTER
   └─ user 10

Zone: FRONT_PASSENGER seat ROW_1_RIGHT
   ├─ DISPLAY_TYPE_MAIN         passenger screen
   └─ user 11

Zone: REAR_PASSENGER_LEFT  seat ROW_2_LEFT
   ├─ DISPLAY_TYPE_MAIN         rear entertainment
   └─ user 12
```

Three zones, five displays, three simultaneous users. Every assumption phone
Android makes about "the current user" and "the display" is now ambiguous.

## Querying the graph

```kotlin title="Walking zones, users and displays"
val zones = car.getCarManager(Car.CAR_OCCUPANT_ZONE_SERVICE)
        as CarOccupantZoneManager

zones.allOccupantZones.forEach { zone ->
    val user = zones.getUserForOccupant(zone)          // may be INVALID_USER_ID
    val main = zones.getDisplayForOccupant(
        zone, CarOccupantZoneManager.DISPLAY_TYPE_MAIN,
    )
    val cluster = zones.getDisplayForOccupant(
        zone, CarOccupantZoneManager.DISPLAY_TYPE_INSTRUMENT_CLUSTER,
    )

    Log.d(TAG, "zone=${zone.zoneType} seat=${zone.seat} user=$user " +
               "main=${main?.displayId} cluster=${cluster?.displayId}")
}
```

The reverse lookups matter just as much:

```kotlin title="Which zone am I running in?"
val myZone = zones.getOccupantZoneForUser(UserHandle.of(myUserId))
val isDriver = myZone?.zoneType == CarOccupantZoneManager.OCCUPANT_TYPE_DRIVER
```

<Callout type="warning" title="&quot;Am I the driver?&quot; is a real question now">
Driver distraction restrictions apply to the driver's displays. A passenger
watching video on their own screen at 100 km/h is legal in many markets; the
same content on the centre stack is not. Code that applies restrictions globally
either blocks the passenger unnecessarily or — much worse — fails to block the
driver.
</Callout>

## Launching onto the right display

```kotlin title="Targeting a display explicitly"
val options = ActivityOptions.makeBasic().apply {
    launchDisplayId = passengerDisplay.displayId
}
context.startActivity(intent, options.toBundle())
```

This needs the right permissions and, for a display belonging to another user,
`INTERACT_ACROSS_USERS`. It is a system-app operation, not something an ordinary
media app does.

## Configuring zones on a product

Zones are declared in platform configuration, mapping seats to display ports:

```xml title="config.xml (product overlay)"
<string-array name="config_occupant_zones">
  <item>occupantZoneId=0,occupantType=DRIVER,seatRow=1,seatSide=driver</item>
  <item>occupantZoneId=1,occupantType=FRONT_PASSENGER,seatRow=1,seatSide=oppositeDriver</item>
  <item>occupantZoneId=2,occupantType=REAR_PASSENGER,seatRow=2,seatSide=left</item>
</string-array>

<string-array name="config_display_uniqueId_to_occupantZone">
  <item>displayPort:0,occupantZoneId=0</item>
  <item>displayPort:1,occupantZoneId=0</item>   <!-- cluster, same zone -->
  <item>displayPort:2,occupantZoneId=1</item>
</string-array>
```

```bash title="Verifying it on a device"
adb shell dumpsys car_service --services CarOccupantZoneService
adb shell dumpsys display | grep -E 'mDisplayId|uniqueId'
```

When a screen stays black on a new board, this pairing is the usual culprit: the
display port in the config does not match what the kernel enumerated.

## What breaks in ordinary code
<Scenario title="An Activity that launched on the wrong screen">
A rear-seat app starts an Activity and it appears on the **centre display**,
in front of the driver.

The cause is almost always a `startActivity` with no display specified. Android
defaults to the display the calling context belongs to — and a service running in
user 0 has no meaningful display, so it lands on the default one.

The fix is explicit:

1. Get the occupant zone for the seat you mean.
2. Ask it for the display ID.
3. Pass that display through `ActivityOptions.setLaunchDisplayId`.

The broader lesson: on a multi-display vehicle, **"the screen" is not a thing**.
Any code that assumes a single display will eventually put something in front of
the wrong person, and on a driving surface that can be a distraction problem
rather than a cosmetic one.
</Scenario>


**Assuming one display.** `WindowManager.getDefaultDisplay()` gives you *a*
display, not necessarily yours. Use the display from your own `Context`.

**Assuming one user.** `ActivityManager.getCurrentUser()` returns the driver's
user. On a multi-zone vehicle a passenger app must ask which zone it is in.

**Global UX restrictions.** Restrictions are per-display. Query them for your
display rather than assuming the driver's set applies.

**Density and geometry.** A cluster is not a tablet. Displays in one vehicle can
differ wildly in size, density and aspect ratio, and resources must be qualified
accordingly.

```kotlin title="Read the display you are actually on"
val display = context.display                    // API 30+
val metrics = context.resources.displayMetrics
Log.d(TAG, "display=${display?.displayId} ${metrics.widthPixels}x${metrics.heightPixels} @${metrics.densityDpi}")
```

## Testing it

```bash title="Exercising multi-display without hardware"
# Add a simulated secondary display to the emulator
adb shell settings put global overlay_display_devices "1280x720/213"

adb shell dumpsys display | grep -c 'Display Device'
adb shell am start --display 2 -n com.example/.PassengerActivity
```

Simulated overlay displays are crude but they catch the whole class of "assumed
display 0" bugs before hardware exists.

<Recap>
- An occupant zone ties a **seat, its displays and a user** together.
- It is what lets the platform know a screen belongs to a passenger rather than
  the driver — which changes the rules that apply to it.
- Query the zone graph rather than assuming; seat and display layout is
  per-product configuration.
- **Always specify a launch display** for Activities on a multi-display vehicle;
  the default is rarely what you meant.
- Ordinary single-display assumptions — "the" display, "the" user, "the" current
  Activity — are the usual source of bugs.
- Test with a real multi-zone configuration; single-display emulators hide all of
  this.
</Recap>
