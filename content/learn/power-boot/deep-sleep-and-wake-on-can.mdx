The previous topic covered the state machine: `ON`, `SHUTDOWN_PREPARE`,
`SUSPEND`, and back. This one is about what "suspend" actually does to the
silicon, and the detail that surprises people coming from phones — the thing
that wakes the head unit back up is very often not the driver at all. It is a
CAN frame.

<Plain>
A phone has one low-power state worth knowing: screen off, radio still
listening for a push notification. A vehicle head unit has several, and the
one it uses most is a full **suspend-to-RAM** — everything off except the bit
of the SoC that keeps DRAM refreshed — woken not by a touch, but by a message
arriving on the vehicle network.
</Plain>

## The two things "sleep" can mean

Linux gives you more than one option, and automotive platforms genuinely
differ on which one they use.

**Suspend-to-RAM** (`S3`, called `mem` in sysfs) freezes every device driver,
gates clocks, and keeps only self-refresh DRAM powered. Resume is fast —
typically under a second — because nothing has to be reloaded, only
re-initialised. This is what "the screen comes back instantly when I open the
door" actually is.

**Hibernation** (`S4`, `disk` in sysfs) writes the entire RAM image to
storage and powers off completely, including DRAM. Resume means reading that
image back, which on flash-based automotive storage is measurably slower than
a suspend-to-RAM resume — and it burns a flash write on every single
power-off. Most head units avoid it for exactly that reason: eMMC and UFS
have a finite number of program/erase cycles, and a vehicle gets turned off
many times a day for years.

In practice the vehicle almost always chooses suspend-to-RAM, and pays for it
with a small standing current draw — which is the subject of the next topic.

<Analogy title="A desk versus a filing cabinet">
Suspend-to-RAM is leaving your desk exactly as it is and turning the office
lights off: nothing moved, and sitting back down costs nothing. Hibernation is
packing the desk into a filing cabinet and starting from an empty desk next
time — slower to resume, but the lights can go all the way off, and the desk
draws no power while it is packed away.
</Analogy>

## Wakeup sources: what is allowed to end a suspend

Suspending only helps if something reliable can end it. Every device that can
wake the system registers itself as a **wakeup source** — visible under
`/sys/class/wakeup` and `/sys/power/wakeup_count` — and the kernel refuses to
re-suspend while one is active. On a phone, the obvious wakeup sources are the
power button and the modem. On a vehicle, the wakeup source that matters most
is the CAN or vehicle-network controller.

A door handle is touched. A body control module puts a frame on the CAN bus
announcing it. The CAN transceiver's interrupt line fires. That interrupt is
a registered wakeup source, which is why the AP resumes even though nothing
touched the AP itself — the wake decision was made entirely on the vehicle
network, milliseconds before Android's suspend/resume path ever runs.

```text title="A representative wake path"
door handle touched
  → body control module transmits CAN frame (e.g. "door unlock request")
  → CAN transceiver interrupt asserts (registered wakeup source)
  → SoC PMIC exits low-power rail state
  → kernel resume: device drivers re-initialise, clocks re-gate on
  → CarService resumes: CarPowerManagementService moves ON
  → surfaces come back, cluster and infotainment race the same boot budget
    covered in the previous topic
```

<Scenario title="On a real programme">
A team ships a build where the head unit resumes reliably on a key fob press
but not on a door handle. The suspicion is a broken CAN wiring harness on the
handle sensor — a hardware bug, reasonable to suspect on a bring-up board.
The real cause is that the handle's wake frame was added to the vehicle
network late, and nobody added its CAN ID to the AP's wakeup filter — the
frame arrives, the transceiver sees it, and the SoC drops it as uninteresting
because it was never told to care. The fix is a one-line filter-table change,
not a rework. Whenever "one input wakes it and another doesn't," suspect the
wakeup filter before the wiring.
</Scenario>

## Why the AP does not wake for every frame

A vehicle network carries hundreds of message IDs at rates up to hundreds of
hertz. If every frame woke the application processor, suspend would save
nothing — the AP would resume constantly for messages it does not care about
while parked. So the CAN wakeup path is filtered: only specific message IDs
(or ranges) are configured as wake-worthy, usually by the platform integrator
in coordination with the vehicle network team, not chosen by app or framework
code. Everything else is dropped by the transceiver or a low-power CAN
controller that can filter frames without ever waking the AP at all — some
SoCs delegate this filtering to a small always-on microcontroller specifically
so the main cores never have to spin up just to discard traffic.

| Wakeup source | Typical trigger | Where it is configured |
| --- | --- | --- |
| CAN frame (filtered) | Door unlock, remote start, alarm event | Wakeup ID table, vehicle-network + platform team |
| RTC alarm | Scheduled Garage Mode window | `alarm` sysfs / `AlarmManager` on the Android side |
| Physical ignition line | Key turned, start button pressed | Board-level GPIO, not CAN at all |
| USB/charge insertion | Cable plugged in while parked | USB PHY wakeup |

<Callout type="warning" title="A CAN wakeup is not a guarantee of correctness">
A frame that wakes the AP does not mean the AP resumed *before* the sender
expected a response. Some vehicle-network messages carry response-time
budgets in the tens of milliseconds. If suspend-to-RAM resume plus Android's
own boot-time budget cannot beat that window, the correct fix is almost never
"make Android faster" — it is moving the time-critical response to a
lower-power domain that never suspended in the first place, and letting
Android answer the slower, human-facing part of the interaction instead.
</Callout>

<Recap>
- Automotive platforms almost always use suspend-to-RAM, not hibernation —
  hibernation's flash write on every power-off wears out storage over a
  vehicle's lifetime.
- Devices that can end a suspend register as **wakeup sources**; the CAN
  controller is normally the most important one in a vehicle.
- Only specific, filtered message IDs wake the AP — most vehicle-network
  traffic is dropped by the transceiver or a low-power controller while
  suspended, or the system would never actually sleep.
- "Wakes for A but not B" almost always means a missing entry in the wakeup
  filter table, not a wiring fault.
- Some response-time budgets are tighter than any Android resume path can
  meet — those belong on an always-on microcontroller, not behind a suspend.
</Recap>
