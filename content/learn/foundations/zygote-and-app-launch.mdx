Tapping an icon doesn't start a fresh Android instance for that app. It
forks one.

<Plain>
<T>Zygote</T> loads every framework class and shared library exactly once,
at boot, then **forks** a copy of itself for each new app. The child
inherits all of that warm state through copy-on-write — no fresh class
loading, no fresh library mapping — and only becomes its final self, with
its own user ID and its own SELinux domain, after the fork completes.
</Plain>

<Analogy title="A photocopier that's already warmed up">
Starting a brand-new Android process from nothing would be like buying a new
photocopier for every document — box it, plug it in, let it warm up, then
copy one page. Zygote is the machine that's already on, already warm,
sitting there mid-copy. Forking a child app is tearing off the next sheet.
</Analogy>

## One zygote, not the name you'd expect

On a 64-bit-only device, the real process name is `zygote64` — `zygote` is
only the init service, socket, and log-tag name.

```bash
adb shell dumpsys meminfo zygote
# No process found for: zygote
adb shell dumpsys meminfo zygote64
# (works)
```

```bash
adb shell ps -A | grep zygote
# root           516     1   ... zygote64
# webview_zygote 1131  516   ... webview_zygote
```

`webview_zygote`'s own parent process ID is `zygote64`'s pid — `zygote64`
forks a second, specialized zygote for WebView content processes, which then
does its own forking for every app that embeds a WebView. A zygote forking a
zygote.

## The wire protocol

`ActivityManagerService` asks for a fork over a plain local socket, with a
protocol about as simple as one gets:

```java title="ZygoteProcess.java"
/*
 * a) a count of arguments (argc, in essence)
 * b) a number of newline-separated argument strings equal to count
 * After the zygote process reads these it will write the pid of
 * the child or -1 on failure, followed by a boolean indicating
 * whether a wrapper process was used.
 */
String msgStr = args.size() + "\n" + String.join("\n", args) + "\n";
```

Real arguments sent for every launch include `--setuid=`, `--setgid=`,
`--nice-name=`, `--seinfo=`, and `--target-sdk-version=`. One access-control
detail worth knowing: the receiving end refuses to even parse a connection
from anyone but the system.

```java title="ZygoteConnection.java"
if (peer.getUid() != Process.SYSTEM_UID) throw new ZygoteSecurityException(...)
```

## A fork, watched end to end

Three independent log lines, three different components, one fork:

```bash
adb shell am force-stop com.example.app
adb shell am start -n com.example.app/.MainActivity
```

```text
ActivityTaskManager: START u10 {cmp=com.example.app/.MainActivity}
ActivityManager: Start proc 2752:com.example.app/u10a167 for next-top-activity
Zygote: Process 2752 created for com.example.app
ActivityTaskManager: Displayed com.example.app/.MainActivity for user 10: +380ms
```

The `Zygote`-tagged line is the most precise: it's logged from inside the
freshly forked child itself, fired right after the SELinux context switch
completes. Everything before it in the child's short life happened as
zygote's own root identity; everything after happens as the app.

## The specialization order isn't arbitrary

The native routine that turns a raw fork into a real app process —
`SpecializeCommon` — runs capability dropping, the uid/gid switch, seccomp,
and the SELinux transition in a fixed order, and the source explains exactly
why:

```cpp title="com_android_internal_os_Zygote.cpp"
// ... need to be able to set our gid/uid... SetUpSeccompFilter() must run
// before setresuid() - it still needs CAP_SYS_ADMIN, and doing it after
// breaks SELinux domain transition.
SetUpSeccompFilter(uid, is_child_zygote);
...
setresuid(uid, uid, uid);
```

<Callout type="warning" title="This isn't the domain transition you'd expect">
No new binary is `exec`'d during a fork, so this can't be an ordinary
`type_transition` the way launching a daemon from init would trigger. It's a
live, in-process **dynamic transition**, explicitly permitted in policy:
```text title="system/sepolicy/private/zygote.te"
allow zygote self:process setcurrent;
allow zygote appdomain:process dyntransition;
```
</Callout>

## Two apps, same domain, for a precise reason

A plain platform-signed app and a `privileged: true` one might be expected to
land in different SELinux domains. Often, they don't:

```bash
adb shell ps -Z -p $(pidof com.example.app)
# u:r:platform_app:s0:c522,c768
adb shell ps -Z -p $(pidof com.example.privapp)
# u:r:platform_app:s0:c522,c768
```

Both land in `platform_app`. The rules that decide a process's domain —
`seapp_contexts` — are matched by a fixed specificity ranking, not file
order, and a specified `seinfo=` field outranks a specified `isPrivApp=`
field in that ranking. Both apps here declare `certificate: "platform"` in
their build file, which produces `seinfo=platform` — so the `seinfo` rule
matches first for both, regardless of one being privileged. The MLS
categories (`c522,c768`) are real too — the same per-user isolation
mechanism behind occupant-zone separation.

## The copy-on-write payoff, measured

```bash
adb shell dumpsys meminfo 516
#                Pss  Private  Private     Rss
#              Total    Dirty    Clean    Total
#  .so mmap    15181       44     9416    62564
#  .jar mmap   11207        0     4312    62444
# TOTAL PSS    34229              TOTAL RSS 197732
```

Zygote's real resident size (RSS) is close to 200 MB, but its *proportional*
share (PSS — the metric that accounts for sharing across processes) is only
about 34 MB, roughly 17%. The `.so` and `.jar` mmaps in particular show real
RSS more than 4x their private-dirty size — the rest is exactly the shared,
copy-on-write pages every forked app process inherits for free instead of
loading itself.

## What's preloaded, and why some of it never loads

Zygote warms up three kinds of state before it ever forks: preloaded
classes, preloaded resources, and preloaded shared libraries. Not every
declared class necessarily loads on every product:

```bash
adb logcat -s Zygote:I | grep -i preload
# Preloading classes...
# ...preloaded 18795 classes in 330ms.
```

<Callout type="note" title="A shared preload list carries some dead entries by design">
A product that excludes an entire subsystem — telephony, say — will log
explicit `Class not found for preloading` warnings for every telephony class
in the shared list. This is real, harmless drift, not a bug: `preloaded-classes`
is one generic list shared across every AOSP product, and individual products
are expected to carry some entries that don't apply to them.
</Callout>

## USAP: present in source, usually off

A second layer — the Unspecialized App Process pool, which pre-forks
generic, not-yet-specialized processes ahead of time — is fully wired into
the zygote server on most trees but commonly ships disabled:

```bash
adb shell getprop dalvik.vm.usap_pool_enabled
# false
```

Worth checking rather than assuming on any given build — the sockets and
refill logic exist either way, but only matter if the flag is on.

## Keyword reference

| Term | What it is |
| --- | --- |
| `zygote64` | The real process name on a 64-bit-only build; `zygote` is only the service/socket/tag name |
| `/dev/socket/zygote` | Plain-text argc+args protocol, system-UID-only, used to request a fork |
| `SpecializeCommon` | The native post-fork routine: capabilities, uid/gid, seccomp, SELinux, in a fixed, load-bearing order |
| Dynamic transition | The SELinux mechanism zygote uses to switch a live process's domain without an `exec` |
| `seapp_contexts` specificity | Source-defined precedence for which rule wins when more than one matches — not file order |
| PSS vs. RSS | PSS counts a shared page once, divided across holders; RSS counts it in full for every process holding it |
| USAP pool | Pre-forked, unspecialized process pool; present in source, commonly disabled by default |
