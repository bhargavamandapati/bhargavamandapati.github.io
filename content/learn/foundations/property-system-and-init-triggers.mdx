`boot-sequence` showed `init` starting services in phases, ending with
`property:sys.boot_completed=1` as the trigger for everything deferrable.
That single example is doing a lot of quiet work: the **property system** is
the mechanism `init` uses to communicate with itself and with every process
on the device, and understanding it is the difference between "boot got
stuck somewhere" and knowing exactly which trigger never fired.

<Plain>
A **system property** is a small, named piece of global state — a string,
readable by any process with permission, settable by `init` triggers or by a
process with the right SELinux label. `sys.boot_completed=1` is one example.
There are thousands of others, covering everything from build fingerprints
to feature flags to per-vendor configuration, and `init`'s entire startup
sequence is driven by watching them change.
</Plain>

## Namespaces are permission boundaries, not just naming conventions

Property names are not arbitrary strings — their prefix determines who can
read and write them, enforced by SELinux `property_contexts`, not by
convention alone.

<Plain>
**SELinux**, in brief, is Android's mandatory-access-control layer — a set of
kernel-enforced rules that sit below and independent of ordinary Unix file
permissions. Every process runs inside a **domain**; every resource it might
touch, including a property, has a **type**. A policy file explicitly lists
which domains may do what to which types, and anything not explicitly
allowed is denied by default, silently, with no exception thrown to the
caller. That denial is what shows up in the kernel log as an
**`avc: denied`** line — it is worth learning to recognise on sight, because
it is the only visible trace of an SELinux-blocked write.
</Plain>

| Prefix | Meaning | Typical writer |
| --- | --- | --- |
| `ro.*` | Read-only after first boot | Set once from build config, immutable after |
| `persist.*` | Survives a reboot | Written to `/data/property`, settable by privileged processes |
| `sys.*` | Volatile system state | `init` and system-privileged processes |
| `vendor.*` | Vendor/HAL-owned state | Vendor HALs and vendor-privileged processes |
| `ctl.*` | Service control commands | A privileged process such as `system_server` (via `SystemProperties.set`), or shell on userdebug — `init` *enforces and executes* `ctl.start`/`ctl.stop`, it is not usually the one setting the property |

Every one of these is checked against a `property_contexts` file that maps
a property name (or prefix) to an SELinux type, and a process's own SELinux
domain determines which types it may set. A vendor HAL trying to set a
`sys.*` property it has no label for does not get a confusing runtime error
— the write is silently denied by SELinux, and unless you already know to
check `dmesg` for an `avc: denied` line, the symptom just looks like the
property never changed.

## Triggers: how init reacts to property changes

`init`'s configuration language supports `on property:<name>=<value>`
triggers directly — `boot-sequence` showed the most famous one, but this
pattern is how init reacts to *any* condition worth waiting for, not only
boot completion.

```text title="A representative property trigger"
on property:vendor.vehiclehal.ready=1
    start vendor.car-service-helper

on property:sys.boot_completed=1 && property:vendor.vehiclehal.ready=1
    class_start late_start
```

Triggers can combine multiple conditions with `&&`, which is exactly how a
platform expresses "do not start the late-boot service class until *both*
the framework has finished booting *and* the vendor VHAL implementation has
confirmed it is ready" — two independent readiness signals, from two
different parts of the stack, joined into one gate.

<Analogy title="A relay race baton, not a memo">
A regular variable is like a memo — whoever reads it later sees whatever it
currently says. A property with a trigger attached is a relay baton: the
moment it changes hands (the value changes), whoever is waiting for exactly
that handoff reacts immediately, without having to keep asking "has it
changed yet?"
</Analogy>

## Where boot actually stalls, at this layer

`boot-sequence`'s own debugging section covers the symptom "one missing
component stalls the whole thing" at the level of which stage failed. This
is the same failure mode one layer deeper: a `class_start` gated on a
property that never gets set, because the process responsible for setting it
crashed silently, was denied by SELinux, or was built with a typo in the
property name that no compiler could catch — property names are just
strings, and a trigger watching for `vendor.vehicelhal.ready` will wait
forever for a process setting `vendor.vehiclehal.ready`.

<Scenario title="On a real programme">
A vendor HAL bring-up stalls boot indefinitely on new hardware, with no
crash and no error in the HAL's own log. `getprop vendor.vehiclehal.ready`
returns empty. The HAL's code sets the property correctly; the property
itself was never added to `property_contexts` for the new board's vendor
policy, so the `setprop` call is silently denied by SELinux before it ever
takes effect — visible only as an `avc: denied` line in the kernel log that
nobody thought to check, because the failure looked like a hang, not a
permission error. The fix is one line in one policy file. The lesson is
that a property-gated trigger that never fires needs `dmesg` checked for an
SELinux denial before anything else, because a silent permission failure
and a silently-crashed writer produce the exact same symptom: the property
simply never changes.
</Scenario>

<Callout type="tip" title="getprop, setprop, and where persist.* actually lives">
`adb shell getprop <name>` reads any property you have permission to see;
`adb shell setprop <name> <value>` writes one, subject to the same SELinux
check every other writer faces. `persist.*` properties are additionally
backed by files under `/data/property` — on a device where `/data` is not
yet mounted (very early boot), a `persist.*` property read returns its
default, not a stale previous value, which is a common source of "why did
this setting reset" confusion during early-boot debugging.
</Callout>

<Recap>
- The property system is a small, globally-readable key-value store that
  `init` both drives and reacts to — `sys.boot_completed=1` from
  `boot-sequence` is one instance of a much more general pattern.
- Property name prefixes (`ro.`, `persist.`, `sys.`, `vendor.`, `ctl.`) are
  permission boundaries enforced by SELinux `property_contexts`, not just a
  naming convention — a missing label produces a silent, not a loud, denial.
- `on property:<name>=<value>` triggers, including combined conditions with
  `&&`, are how init gates a service class on multiple independent
  readiness signals from different parts of the stack.
- A trigger that never fires and a writer that was silently SELinux-denied
  produce the identical symptom — check `dmesg` for an `avc: denied` line
  before assuming the writer itself is broken.
</Recap>
