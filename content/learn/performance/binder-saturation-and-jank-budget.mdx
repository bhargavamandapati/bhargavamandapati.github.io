`binder-and-aidl` already covered the mechanism: a finite per-process thread
pool, and how one slow call can exhaust it and stall unrelated callers. This
topic assumes that mechanism as background and asks a narrower question —
what happens to it specifically during the ten seconds after boot, when
every app on the head unit is cold-starting at once and all of them reach
for the same process, `CarService`, at roughly the same moment. That window
is where thread-pool pressure stops being an occasional slow-HAL problem and
becomes a predictable, everyday one.

<Plain>
A single slow call exhausting a thread pool is a bug in one HAL
implementation. Multiple apps *simultaneously and correctly* subscribing to
vehicle properties during cold start is not a bug anywhere — every call is
individually fast and well-behaved — and it can produce the exact same
symptom, because the pool has a fixed size regardless of whether the
pressure comes from one slow caller or several fast, concurrent ones.
</Plain>

## Why cold start is the worst-case window

`carservicehelper` and any long-running vendor HAL implementation each carry
their own bounded thread pool — commonly capped around 15 threads by default.
`system_server` is the notable exception: it hosts so many system services
that it raises its own binder thread-pool ceiling well above that default,
though the ceiling is still finite and can still be exhausted under enough
concurrent load. Car Service is the process nearly every vehicle-property
read and every occupant-zone lookup passes through, which makes its pool a
shared resource across every app on the head unit at once. Cold start is
when demand on that shared pool peaks hardest: it is the one moment when the
cluster, the launcher, and every pre-installed app are all initialising
their vehicle-property subscriptions within the same few hundred
milliseconds, each call individually well within budget, the pool itself
the bottleneck.

```text title="Why concurrent, well-behaved calls still queue"
App A: subscribe to PERF_VEHICLE_SPEED  ──┐
App B: subscribe to HVAC_TEMPERATURE_SET ─┤──► CarService Binder thread pool
Cluster: subscribe to ENGINE_RPM          ──┘        (bounded, shared)

five more pre-installed apps do the same in the same boot window
  → the pool is not idle waiting for a slow outlier, it is simply full
  → the sixth arriving call queues — not because anything is broken,
    but because the previous five have not finished yet
  → if enough threads are similarly stuck, ALL of them queue
  → none of the three apps did anything wrong
```

## Oneway calls: the escape hatch, and a different cost

`binder-and-aidl` covered `oneway` as a deadlock-avoidance tool — a
notification that does not block lets a service avoid waiting on a listener
that might call straight back into it. It has a second, separate cost that
matters specifically for the subscription-heavy, cold-start-heavy pattern
this topic is about: backpressure. Oneway transactions from the same
caller to the same target are still queued and delivered in order, but if the
*receiver* falls behind, that queue grows without the sender ever finding
out — there is no blocking to signal "slow down." A property-update listener
that does expensive work on receipt can silently build a backlog of pending
callbacks, each individually harmless, collectively a memory and latency
problem that shows up as "updates feel delayed" rather than as any single
identifiable failure.

<Analogy title="A phone call versus a stack of notes">
A blocking Binder call is a phone call — you cannot hang up until the other
side answers, so if they are busy, you are stuck too. A `oneway` call is
leaving a note on someone's desk — you walk away immediately regardless of
whether they are free, but if you leave notes faster than they read them,
the stack on their desk just keeps growing, and nothing tells you that until
someone notices the desk.
</Analogy>

## What this costs the cold-start jank budget

`app-startup-and-responsiveness` already covered the startup budget in
general terms; Binder saturation is one of the least visible ways to blow
it. A cold-started app that immediately fires off several synchronous
vehicle-property reads on its main thread — reasonable-looking code, one
call per property — is making several blocking round trips through a
possibly-contended shared thread pool, during the exact window when the
system is also busiest: every other app on the head unit is cold-starting
too, all reaching for Car Service at once.

<Scenario title="On a real programme">
A cluster app passes every isolated performance test and then shows a
visible stutter specifically during the first three seconds after boot, on
vehicles with more pre-installed apps than the reference configuration. A
Perfetto trace shows the cluster's Binder call to `CarPropertyManager`
sitting in `binder transaction` state for over 100 ms — not because the
call itself is slow, but because five other apps are cold-starting at the
same instant and Car Service's thread pool is momentarily saturated
servicing all of them. Optimising the cluster app's own code changes
nothing; the fix is staggering non-critical property subscriptions across
apps during the boot window, so the shared pool is not fighting for the
same few threads for every one of them simultaneously.
</Scenario>

<Callout type="tip" title="Binder time is visible in a trace, and easy to miss without one">
`adb shell dumpsys` and a stack sample will show a thread blocked "in
Binder," but not *why* — whether it is waiting on a slow HAL, a saturated
thread pool, or a genuinely slow remote method. A Perfetto trace with binder
tracing enabled shows both sides of the transaction and how long each spent
where, which is the only reliable way to tell those three apart.
</Callout>

<Recap>
- Thread-pool exhaustion does not require a slow or broken call — enough
  concurrent, individually well-behaved calls into the same shared process
  (like Car Service) saturate the pool just as effectively.
- Cold start is the worst-case window for this precisely because it is when
  demand on that shared pool peaks: every app on the head unit initialising
  its property subscriptions within the same few hundred milliseconds.
- `oneway` calls avoid blocking the sender but can silently queue on the
  receiver if it falls behind — a backlog with no signal to the sender that
  it is happening.
- Cold-start jank from Binder contention is most visible during the exact
  window every app is fighting for the same shared thread pool at once —
  reproduce it under realistic multi-app boot load, not in isolation.
- A Perfetto trace with binder tracing is the only reliable way to
  distinguish "the HAL is slow" from "the thread pool is saturated."
</Recap>
