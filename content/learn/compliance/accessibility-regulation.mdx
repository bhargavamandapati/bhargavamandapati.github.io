`accessibility` in the HMI module covers how to build it correctly — touch
target sizes, focus order, content descriptions, contrast. This topic is
the regulatory layer sitting above that implementation work: which of it is
actually mandated by law, in which markets, and what a compliance audit
checks for that a design review alone would not catch.

<Plain>
"We built it accessible" and "we can prove it meets the regulation" are
different claims, checked by different people, at different points in a
programme. The implementation topic makes the first claim achievable. This
one is about the second — the evidence, the standard it is measured against,
and the fact that "good UX practice" and "legal requirement" do not always
draw the line in the same place.
</Plain>

## The standard that actually applies

**EN 301 549** is the EU's accessibility requirements standard for ICT
products and services, and it is the one most automotive HMI accessibility
requirements trace back to in European markets — it was written for a much
broader set of products than vehicles, but its requirements for software
user interfaces apply directly to an infotainment or cluster HMI without
needing an automotive-specific rewrite. It in turn incorporates **WCAG**
(the Web Content Accessibility Guidelines) by reference for large parts of
its software criteria, which is why a WCAG conformance level (typically AA)
shows up in automotive accessibility requirements documents that otherwise
have nothing to do with the web.

<Analogy title="A building code borrowed from a different kind of building">
EN 301 549 was written to cover software broadly — a bank's ATM interface,
a public kiosk, a phone app — and a vehicle HMI is required to meet the same
bar because it is, in the regulation's terms, still just software with a
user interface. It is less like a bespoke automotive accessibility law and
more like a general building code being applied to a building type nobody
was specifically picturing when it was written — the requirements still
apply, they just were not designed with a steering wheel in the room.
</Analogy>

## Where "good practice" and "legal requirement" genuinely diverge

Most of what `accessibility` already covers — proper content descriptions,
adequate touch targets, sufficient contrast — is both good practice and
required by the standard; there is no tension there. The divergence shows
up in specifics an implementation-focused review would not necessarily
flag on its own:

| Requirement | Why it is easy to miss without the regulation in view |
| --- | --- |
| A minimum contrast ratio, numerically specified | "Looks readable" is a design judgement; the regulation specifies a number, checked with a tool, not an opinion |
| Text resizing without loss of functionality | A layout that merely *looks* fine at default size may break at the resize levels the standard actually requires supporting |
| Non-text content requires a text alternative, with narrow exceptions | An icon-only control that "everyone understands" is not automatically exempt; the exceptions are specific and narrower than intuition suggests |
| Time limits on an interaction must be adjustable or removable, with narrow exceptions | A UX-restriction-driven timeout, added for driver distraction reasons, can itself create an accessibility gap if it cannot be extended |

<Callout type="warning" title="A UX-restriction decision and an accessibility requirement can pull in different directions">
A short timeout on an interaction is often the right call for driver
distraction. The same timeout can conflict with an accessibility
requirement for a user who needs more time to complete it — a driver using
a switch-access-style input, for instance. Resolving this is a genuine
design trade-off, not a checkbox; it usually means the timeout logic needs
to know about assistive-technology use specifically, rather than applying
one fixed value to everyone.
</Callout>

## What an audit actually checks

A regulatory accessibility audit does not review your code — it exercises
the built product against the standard's success criteria, largely with
the same tools an end user's assistive technology would use, and it
produces a compliance report (an **Accessibility Conformance Report**, often
in the VPAT format used across several markets) documenting which criteria
pass, which do not, and, honestly, which do not apply to this kind of
product at all.

<Scenario title="On a real programme">
A cluster HMI passes internal accessibility review — every team member
manually confirmed the touch targets, contrast and content descriptions
looked right — and then fails a formal audit on a criterion nobody had
tested directly: whether a screen's essential information remains
available when TalkBack-style navigation is used exclusively, with no
touch input at all. The internal review had validated the visual and touch
experience thoroughly and never actually attempted the flow with the
assistive-technology path alone. The fix is adding that specific
walkthrough — complete a core task using only the accessibility service, no
touch — to the review checklist, not as a spot check but as a required pass
before every release, because it was the one path the rest of the process
never actually exercised.
</Scenario>

## What lands on an AAOS engineer specifically

The good news is that most of the mechanism `accessibility` already
covers — content descriptions, focus order, TalkBack support — is exactly
what a formal audit checks, so building it correctly the first time is not
extra work layered on top of compliance; it largely *is* the compliance
work. What is worth adding specifically for the regulatory case: keep a
record of *how* each requirement was verified (which tool, which build,
which criterion), because an audit wants evidence of a process, not just a
final state that happens to pass — and test the assistive-technology-only
path as its own explicit case, not as a side effect of testing the visual
one.

<Recap>
- EN 301 549, incorporating WCAG for much of its software criteria, is the
  standard most automotive HMI accessibility requirements trace back to in
  European markets — written for ICT broadly, applied to a vehicle HMI
  without an automotive-specific rewrite.
- Good implementation practice and legal requirement mostly overlap, but
  diverge on specifics — numeric contrast ratios, resize support, narrow
  exemption criteria — that a purely visual design review will not
  reliably catch.
- A UX-restriction timeout and an accessibility time-limit requirement can
  genuinely conflict; resolving it usually means the timeout needs to be
  assistive-technology-aware, not simply longer for everyone.
- An audit exercises the built product with real assistive-technology
  tools and expects documented evidence of how each criterion was
  verified — test the accessibility-only path as its own explicit case,
  not as a side effect of testing the visual one.
</Recap>
