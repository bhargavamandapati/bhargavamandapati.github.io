The RRO tutorial covered theming CarSystemUI and the Car UI Library from a
separate APK — no rebuild, thirty-second iteration. This one covers the
resources that trick stops working on: anything a target module never marked
overlayable, and anything read before the overlay manager is even running.
For those, the fix is older, cruder, and unavoidable — a build-time overlay.

<Callout type="warning" title="Development target, not a production vehicle">
These overrides apply to the fictional `vega` build for learning purposes.
Overriding framework behaviour on a real vehicle's software is a change to a
shipped product and belongs in that OEM's own build and review process.
</Callout>

<FileTree>
device/oem/vega/
├── overlay/
│   └── frameworks/base/core/res/res/values/
│       └── config.xml            # replaces the framework default, whole file
├── overlay-carlauncher/
│   └── packages/apps/Car/Launcher/res/values/
│       └── config.xml            # replaces a Car Launcher default
└── vega.mk                       # DEVICE_PACKAGE_OVERLAYS +=
</FileTree>

## The two mechanisms, and why both exist

A **static overlay** is a resource file that Soong builds *in place of* the
original at compile time. There is no runtime decision — the value baked
into the boot image is whichever file the build picked up last. It works on
any resource in any module, because it is not a feature the target module
opted into. Resolution happens per resource *name*, not per file: a value
you list here replaces the base file's value outright, but any resource you
do not repeat is still inherited from the base file individually — you are
not required to reproduce every entry `config.xml` defines, only the ones
you actually want to change.

An **RRO** is a real APK, installed and resolved by `ResourceManager` after
boot, against resources the target explicitly declared overlayable via an
`<overlayable>` block. It is reversible at runtime (`cmd overlay
disable`), it can ship as an update without a new system image, and it can
target only the handful of values you actually care about. Its entire
mechanism depends on the target package having opted in — a resource with no
`<overlayable>` entry is not reachable by any RRO, no matter how the overlay
is written or signed.

<Plain>
If the resource is marked overlayable, use an RRO — it is safer and it
ships without a rebuild. If it is not, or if it has to be correct before
the overlay service is even up, a static overlay is the only mechanism that
reaches it at all. This tutorial is for the second case.
</Plain>

## Step 1 — Override a framework-wide default

`config_enableNightDisplay` is a real platform boolean, defined in
`frameworks/base/core/res/res/values/config.xml`, that gates whether Night
Light is offered at all. Suppose vega's climate and lighting are handled
entirely by the vehicle, and the feature should not appear.

```bash title="Create the overlay directory, mirroring the module's own path"
mkdir -p device/oem/vega/overlay/frameworks/base/core/res/res/values
```

```xml title="device/oem/vega/overlay/frameworks/base/core/res/res/values/config.xml"
<?xml version="1.0" encoding="utf-8"?>
<resources>
    <!-- Handled by the vehicle's own lighting system — not a phone feature
         here, and duplicating it confuses the driver about which system is
         actually in charge. -->
    <bool name="config_enableNightDisplay">false</bool>
</resources>
```

<Gotcha title="This file replaces the target's config.xml, not merges with it">
Soong's overlay resolution is per resource *name*, not per file — resources
present in the base `config.xml` that you do not repeat here are still
inherited individually. It looks like a merge for that reason, and mostly
behaves like one. What it will not do is let you reference or extend a value
from the base file inside this one; each entry here is a complete
replacement of that one resource, nothing partial.
</Gotcha>

## Step 2 — Point the build at it

```makefile title="device/oem/vega/vega.mk"
DEVICE_PACKAGE_OVERLAYS += device/oem/vega/overlay
```

`DEVICE_PACKAGE_OVERLAYS` is a *list* — later entries win on conflicts —
which is how a product can layer a generic automotive overlay with a
region-specific one on top, both changing the same resource, without either
one being edited.

## Step 3 — Do the same for a module that is not part of the framework

Static overlays are not limited to `frameworks/base`. Any module built with
Soong can be overlaid the same way, at its own path.

```bash
mkdir -p "device/oem/vega/overlay-carlauncher/packages/apps/Car/Launcher/res/values"
```

```xml title="device/oem/vega/overlay-carlauncher/packages/apps/Car/Launcher/res/values/config.xml"
<?xml version="1.0" encoding="utf-8"?>
<resources>
    <!-- Car Launcher's app-grid column count. Not exposed through any RRO
         because packages/apps/Car/Launcher never declared it overlayable —
         a static overlay is the only path to it. -->
    <integer name="car_launcher_num_columns">5</integer>
</resources>
```

```makefile title="device/oem/vega/vega.mk — add the second path"
DEVICE_PACKAGE_OVERLAYS += \
    device/oem/vega/overlay \
    device/oem/vega/overlay-carlauncher
```

<Gotcha title="A resource this reaches, an RRO could not — check both ways">
Before reaching for a static overlay, check the target module's resources
for an `<overlayable>` block (`res/values/overlayable.xml`, usually). If the
resource is listed, an RRO is strictly better: it survives without a
rebuild, and a reader six months from now can toggle it with `cmd overlay`
to confirm what it does. Reach for a static overlay only once that check
comes back empty, or the resource resolves before boot has anywhere to run
an RRO at all.
</Gotcha>

## Step 4 — Build and verify

```bash title="Rebuild and confirm both values landed"
cd ~/aosp && source build/envsetup.sh
lunch vega-trunk_staging-userdebug
m -j
```

```bash title="Relaunch on the freshly built image — the running emulator is still on the old one"
emulator -verbose -no-snapshot &
adb wait-for-device
sleep 30
```

<Verify title="Verify the overridden values, not just that the build succeeded">
```bash
adb shell dumpsys car_service | grep -i launcher          # sanity: launcher is the one you expect

# Pull the actual compiled resource table and inspect it directly —
# this is the check that cannot be fooled by a stale APK on the device.
aapt2 dump resources $ANDROID_PRODUCT_OUT/system/framework/framework-res.apk \
  | grep -A2 config_enableNightDisplay
```
The `aapt2` output should show `false`, matching the overlay — not the
upstream default, and not whatever the last RRO you tested happened to set,
since a static overlay is not something `cmd overlay list` will ever show
you.
</Verify>

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| Value unchanged after a full rebuild | `DEVICE_PACKAGE_OVERLAYS` path is wrong, or missing from the product actually being built |
| Value changes, but only sometimes | Two overlay directories both touch the resource; check list order — later wins |
| Resource "not found" at build time | Path under `overlay/` does not mirror the target module's own resource path exactly |
| Change works in AOSP, vanishes after a merge | A later `DEVICE_PACKAGE_OVERLAYS +=` in an included product config landed after yours |
