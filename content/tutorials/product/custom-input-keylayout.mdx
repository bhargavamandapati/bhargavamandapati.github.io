A steering wheel button is, to the kernel, a raw scancode on an input
device with no idea what a `KEYCODE_VOICE_ASSIST` is. Two small text files —
never compiled, never imported by any app — are what turn that scancode
into something `Activity.onKeyDown()` can actually receive. Get the device
name in either file wrong and the button does nothing, silently, with no
exception anywhere to catch.

<FileTree>
device/oem/vega/
├── usr/keylayout/
│   └── Vega_Steering_Wheel.kl
└── usr/idc/
    └── Vega_Steering_Wheel.idc
</FileTree>

## How Android finds the right files at all

When an input device is hotplugged (or enumerated at boot), `InputReader`
asks the kernel for the device's advertised name — the same string
`EVIOCGNAME` returns, and the same one `cat
/proc/bus/input/devices` shows next to `N:`. It then looks for
`<that name, spaces turned into underscores>.kl` and `.idc` under
`/vendor/usr/keylayout/` and `/vendor/usr/idc/`. There is no manifest, no
registration step — the device's own name *is* the lookup key, which is
exactly why getting it right (and matching it exactly, including case)
is the entire game.

<Plain>
The device does not know it is "the steering wheel" — it only knows the
name string its own kernel driver reports. Android's whole matching scheme
rests on that string being unique and unchanging, which is why the very
first step of any input bring-up is reading it directly off the device
rather than guessing at what it probably is.
</Plain>

## Step 1 — Find the device's real name

```bash title="On the target, before writing anything"
adb shell cat /proc/bus/input/devices
```

```text title="Representative output for vega's steering wheel"
I: Bus=0019 Vendor=0000 Product=0001 Version=0000
N: Name="Vega Steering Wheel"
P: Phys=vega-can-input/input0
S: Sysfs=/devices/virtual/input/input4
U: Uniq=
H: Handlers=event4
B: EV=13
B: KEY=1000000000007
```

`N: Name="Vega Steering Wheel"` is the string that matters. Spaces become
underscores in the filename, so this device's files are
`Vega_Steering_Wheel.kl` and `Vega_Steering_Wheel.idc` — not "steering
wheel," not "vega-steering-wheel," exactly that string with exactly that
transform.

<Gotcha title="Confirm the name on the real hardware — do not assume it from a datasheet">
A CAN-bridged input device (buttons arriving as CAN frames, translated into
`input_report_key()` calls by a kernel driver, per the CAN-signal bridging
topic earlier in this curriculum) gets whatever name string that driver's
author chose to report — which is not necessarily what the vehicle
integration spec calls it. Always read `/proc/bus/input/devices` on the
actual board.
</Gotcha>

## Step 2 — Write the key layout file

```text title="device/oem/vega/usr/keylayout/Vega_Steering_Wheel.kl"
# Scancode → Android keycode. The left column is whatever the driver reports;
# the right column is a real android.view.KeyEvent constant.
key 1   VOICE_ASSIST
key 2   MEDIA_NEXT
key 3   MEDIA_PREVIOUS
key 4   VOLUME_UP
key 5   VOLUME_DOWN
key 6   CALL
key 7   ENDCALL
```

<Gotcha title="The scancode on the left is not something you invent — read it, do not guess it">
```bash title="Confirm the real scancodes with getevent"
adb shell getevent -lt /dev/input/event4
```
Press each physical button once and note the `KEY` scancode `getevent`
reports. A `.kl` file with invented scancodes builds and installs without
error and simply never matches a real key press — there is no validation
step that catches a wrong number here.
</Gotcha>

## Step 3 — Write the input device configuration file

The `.idc` file describes *how* the device should be treated, separately
from what each key means.

```text title="device/oem/vega/usr/idc/Vega_Steering_Wheel.idc"
# This is a key-only device — no touch, no cursor.
device.type = external

# Steering-wheel buttons should work identically regardless of which
# occupant zone currently has display focus.
input.orientationAware = 0
```

## Step 4 — Wire both files into the build

```makefile title="device/oem/vega/vega.mk"
PRODUCT_COPY_FILES += \
    device/oem/vega/usr/keylayout/Vega_Steering_Wheel.kl:$(TARGET_COPY_OUT_VENDOR)/usr/keylayout/Vega_Steering_Wheel.kl \
    device/oem/vega/usr/idc/Vega_Steering_Wheel.idc:$(TARGET_COPY_OUT_VENDOR)/usr/idc/Vega_Steering_Wheel.idc
```

```bash
cd ~/aosp && source build/envsetup.sh
lunch vega-trunk_staging-userdebug
m -j
```

<Verify title="Verify the files landed, then verify the mapping actually works">
```bash
# Step A: the files exist where InputReader looks for them
adb shell ls /vendor/usr/keylayout/ /vendor/usr/idc/

# Step B: InputReader picked up the .kl for this specific device
adb shell dumpsys input | grep -A5 "Vega Steering Wheel"

# Step C: a real press produces a real Android KeyEvent, not just a raw scancode
adb shell getevent -lt /dev/input/event4     # raw scancode, from the kernel
# press the voice-assist button now — confirm KEY_1 (or whichever scancode you mapped) appears
```
`dumpsys input` should show the device with `KeyLayoutFile` and
`KeyCharacterMapFile` both resolved to real paths, not `<none>`. A `<none>`
there means the name match failed — recheck the exact string from Step 1
against the filenames byte for byte.
</Verify>

## Step 5 — Confirm an app actually receives it

```bash title="Watch key events arrive at the window manager"
adb shell dumpsys window trace &
adb shell input keyevent --help > /dev/null  # just confirms the shell path works
```

Press the physical voice-assist button and watch logcat:

```bash
adb logcat | grep -i KeyEvent
```

A correctly mapped button produces a `KeyEvent` with
`keyCode=KEYCODE_VOICE_ASSIST` in the log, dispatched to whichever activity
currently has focus — indistinguishable, from the app's side, from a phone
keyboard's voice button.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| `KeyLayoutFile: <none>` in `dumpsys input` | Filename does not exactly match the device's reported name, including case and underscores |
| Files present, still `<none>` | Files copied to the wrong path — check `TARGET_COPY_OUT_VENDOR` resolved where expected |
| `getevent` shows a scancode, no `KeyEvent` in logcat | `.kl` maps that scancode to a keycode that does not exist, or has a typo in the constant name |
| Works over `adb shell input keyevent`, not from the real button | The synthetic injection bypasses `.kl` entirely — this only proves the app-side handling, not the mapping |

## What you have now

A steering wheel whose buttons arrive in every app as ordinary Android
`KeyEvent`s, matched to the physical hardware by the one string the kernel
itself reports — the same mechanism, unmodified, that maps a USB keyboard's
scancodes on a phone.
