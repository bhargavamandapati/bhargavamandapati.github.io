A dedicated secondary panel — a rear-seat screen, a cluster — often needs to
run exactly one app, permanently, with no way for the user to back out to a
launcher. `FixedActivityService` is AAOS's built-in answer: pin an activity
to a display, and the platform promises to relaunch it if it crashes. No app
code required — it's driven straight from a shell command.

## Step 1 — The command, and its real name

```bash
adb shell cmd car_service help
#   start-fixed-activity displayId packageName activityName
#     Start an Activity the specified display as fixed mode
#   stop-fixed-mode displayId
#     Stop fixed Activity mode for the given display.
```

<Gotcha title="The printed help text is stale — trust the source, not the printout">
Running the command exactly as printed fails:
```bash
adb shell cmd car_service start-fixed-activity 0 com.example.kioskapp .MainActivity
# Unknown command: "start-fixed-activity"
```
The real dispatch constants, a few lines away in the same source file, are
one word longer:
```java
private static final String COMMAND_START_FIXED_ACTIVITY_MODE = "start-fixed-activity-mode";
private static final String COMMAND_STOP_FIXED_ACTIVITY_MODE = "stop-fixed-activity-mode";
```
Every argument, order and flag in the printed usage is otherwise correct —
only the command name itself is missing its `-mode` suffix.
</Gotcha>

## Step 2 — The rule the main display can't pass

```bash title="Correct command, wrong display"
adb shell cmd car_service start-fixed-activity-mode 0 com.example.kioskapp .MainActivity
# Failed to start
# W CAR.AM: Target display cannot be used for fixed mode, displayId:0
```

```java title="FixedActivityService.java"
private boolean isDisplayAllowedForFixedMode(int displayId) {
    if (displayId == Display.DEFAULT_DISPLAY || displayId == Display.INVALID_DISPLAY) {
        Slogf.w(TAG_AM, "Target display cannot be used for fixed mode, displayId:" + displayId, ...);
        return false;
    }
    return true;
}
```

This is a deliberate design boundary, not a bug: fixed mode exists for a
dedicated secondary panel that one app should permanently own. Letting it
claim the main driver display would lock the whole vehicle into one app.

## Step 3 — Manufacture a secondary display to test on

No hardware or emulator flags needed — a standard Android developer-options
trick creates a real second display:

```bash
adb shell settings put global overlay_display_devices "1024x600/240"
adb shell dumpsys window displays | grep mDisplayId
#   Display: mDisplayId=2 (organized)
#   Display: mDisplayId=0 (organized)
```

## Step 4 — Pin the activity

```bash
adb shell cmd car_service start-fixed-activity-mode 2 com.example.kioskapp .MainActivity
# Succeeded
```

<Verify title="Verify the activity is genuinely pinned">
```bash
adb shell dumpsys car_service --services FixedActivityService
# mRunningActivities:{2=RunningActivityInfo{
#   intent:Intent { cmp=com.example.kioskapp/.MainActivity },
#   userId:10, isVisible:true, isStarted:true, ...}}
```
`isVisible:true`, `isStarted:true` — pinned to a real secondary display,
confirmed through the service's own state, not just the shell's exit code.
</Verify>

## Step 5 — The relaunch promise

The entire point of "fixed" mode over a plain launch is what happens after a
crash:

```java title="FixedActivityService.java"
private final ProcessObserverCallback mProcessObserver = new ProcessObserverCallback() {
    @Override
    public void onForegroundActivitiesChanged(int pid, int uid, boolean foregroundActivities) {
        launchIfNecessary();
    }
    @Override
    public void onProcessDied(int pid, int uid) {
        launchIfNecessary();
    }
};
```

This isn't a Car-specific shortcut — it registers a real `IProcessObserver`
straight into `IActivityManager`, the same system-wide death-notification
path core platform components use. Killing the pinned app's process should
trigger `onProcessDied()` → `launchIfNecessary()` → a fresh launch on the
same display.

<Gotcha title="Verify relaunch against a real crash, not just a manual kill">
`FixedActivityService`'s relaunch path is wired to a genuine process-death
callback, and the registration itself is easy to confirm live
(`mEventMonitoringActive:true` in the same dump). But a manually issued
`kill` and an actual in-app native crash don't always exercise process
teardown identically — if a relaunch doesn't appear immediately after a
manual `kill` in your own testing, retest against a real crash before
concluding the mechanism isn't working. Check for the source's own
"Launching Activity for fixed mode" log line as the definitive signal, not
just the absence of the old activity.
</Gotcha>

## Step 6 — Clean up

```bash
adb shell cmd car_service stop-fixed-activity-mode 2
adb shell settings put global overlay_display_devices none
```

Both take effect immediately — `mRunningActivities` clears, and the
simulated display disappears.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| `Unknown command: "start-fixed-activity"` | Use `start-fixed-activity-mode` — the shell help text is missing the suffix |
| `Failed to start` naming `displayId:0` | Fixed mode rejects the default display by design — test against a secondary one |
| No secondary display to test against | Create one with `settings put global overlay_display_devices "WxH/dpi"` |
| Relaunch doesn't appear to fire after a manual `kill` | Confirm `mEventMonitoringActive:true` first, then retest against a real in-app crash before concluding the path is broken |
