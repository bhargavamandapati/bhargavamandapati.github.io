Plenty of ordinary Android apps assume a phone-shaped screen. On a wide,
unusually-shaped, or multi-display car screen, that assumption shows up as
layouts that overflow, controls that land off-center, or text that renders
too small to read at arm's length. Rather than stretch the app or block it
outright, AAOS can scale it down as a whole — a mechanism most readers never
notice, because it logs one line and otherwise stays invisible.

## Step 1 — Confirm the feature is live

```bash
adb shell pm list features | grep display
# feature:android.software.car.display_compatibility

adb shell device_config list car_framework | grep display_compat
# display_compatibility=true
# display_compatibility_density=true
```

Both the system feature and the runtime flags are on. What's missing on many
builds is a single config file.

<FileTree>
packages/services/Car/car_product/displaycompat/
└── display_compat_config.xml   # default scale, reached only through car_base.mk
</FileTree>

```xml title="display_compat_config.xml"
<config>
    <scale display="0">0.7</scale>
</config>
```

<Gotcha title="A missing file can be a product-inheritance gap, not a missing feature">
A product that reaches the car product family through a sibling chain
(rather than through `car_base.mk` directly) can pull in the feature flags
and the scaling engine itself, but never this one config module. The
symptom is a caught, logged `FileNotFoundException` in any app that reads
its own compat config directly — not a crash, since the activity finishes
launching a moment later regardless — but confirmation the default is simply
absent on that product.
</Gotcha>

## Step 2 — Override it live, no rebuild

The scale table isn't only file-backed — it's cached into a real
`Settings.Secure` key, watched by a `ContentObserver`.

```bash title="Read the current table"
adb shell settings get secure android.software.car.display_compatibility:settings:secure
```

<Gotcha title="Target the current user, not user 0">
The scale table is per-package, per-user, per-display. Writing an entry for
the wrong user ID silently does nothing for what you're looking at.
Confirm which user is actually active first:
```bash
adb shell am get-current-user
```
</Gotcha>

```bash title="Write a real override"
adb shell settings put secure android.software.car.display_compatibility:settings:secure \
  '<config><scale display="0" packageName="com.example.displaycompattest" userId="10">0.6</scale></config>'

adb shell am force-stop com.example.displaycompattest
adb shell am start -n com.example.displaycompattest/.MainActivity
```

<Verify title="Verify the new scale actually took effect">
```bash
adb logcat -d | grep CarDisplayCompatScaleProviderUpdatableImpl
# Returning CompatScale CompatScaleWrapper{
#   mScaleFactor=1.0, mDensityScaleFactor=0.6, mOverrideDensityDisplayIds=[0]}
#   for package com.example.displaycompattest
```
A non-default `CompatScale` — exactly the value just written — returned on
demand, with no rebuild. The missing config file only supplies a *default*;
the per-package override path works independently of it.
</Verify>

Restore the original value afterward with a second `settings put`, so the
device is left exactly as found.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| `Returning CompatScale null` for every package | Expected when nothing has opted in or been overridden yet — not an error |
| App's own config read throws `FileNotFoundException` | `display_compat_config.xml` isn't reachable through this product's inherit chain |
| A `settings put` override seems to do nothing | Check the `userId` in the entry against `am get-current-user` — it must match exactly |
| No shell command surface for this | Expected — there is none; the live path is the `Settings.Secure` key, not `cmd car_service` |
