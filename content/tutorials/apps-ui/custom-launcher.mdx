`packages/apps/Car/Launcher` is what the driver sees before anything else —
the app grid, the media widget, the maps card. Most of what an OEM wants to
change about it is cosmetic, and an RRO reaches all of it. The other thing
an OEM sometimes wants — a genuinely different launcher, built by a
different team, on a different release cycle — is a real replacement, and
replacing the app that owns `HOME` is not something you back out of by
disabling an overlay.

## Step 1 — Theme the stock launcher first

Almost everything visual about Car Launcher is already overlayable —
background, grid spacing, card colours, the media widget's chrome — because
`packages/apps/Car/Launcher` was built expecting OEMs to theme it this way
rather than fork it.

```bash
mkdir -p "device/oem/vega/overlay-launcher/packages/apps/Car/Launcher/res/values"
```

```xml title="device/oem/vega/overlay-launcher/packages/apps/Car/Launcher/res/values/colors.xml"
<?xml version="1.0" encoding="utf-8"?>
<resources>
    <color name="car_launcher_background_color">#0B1220</color>
    <color name="car_launcher_grid_item_selected">#22D3EE</color>
</resources>
```

```makefile title="device/oem/vega/vega.mk"
DEVICE_PACKAGE_OVERLAYS += device/oem/vega/overlay-launcher
```

<Verify title="Verify the theme without touching a single line of Launcher's own source">
```bash
m -j && adb shell reboot
adb wait-for-device
adb shell screencap -p /sdcard/home.png && adb pull /sdcard/home.png
```
Open `home.png`. Background and grid-selection colour should match the
overlay — and `Launcher.apk`'s own signature and build date, checked with
`adb shell dumpsys package com.android.car.carlauncher`, should be
unchanged. Nothing about the app itself was rebuilt.
</Verify>

## Step 2 — Understand what a real replacement actually requires

Suppose the theme is not enough — vega's launcher needs its own data source
for the app grid, not just Car Launcher's colours. Replacing it means
winning **`Intent.CATEGORY_HOME`** at boot, every boot, with no dialog asking
the driver to choose. That is done through `default-permissions.xml`, not a
manifest priority trick — a car has no home screen picker, so the platform
decides this once, at the image level.

```xml title="vendor/oem/vega/apps/VegaLauncher/AndroidManifest.xml (excerpt)"
<activity android:name=".VegaLauncherActivity"
    android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.HOME" />
        <category android:name="android.intent.category.DEFAULT" />
    </intent-filter>
</activity>
```

```xml title="device/oem/vega/sysconfig/default-permissions.xml"
<config>
    <default-permissions>
        <exception package="com.vega.launcher">
            <!-- Grants nothing extra here — this file's role is establishing
                 com.vega.launcher as the platform's chosen HOME resolver,
                 configured separately below. -->
        </exception>
    </default-permissions>
</config>
```

```xml title="device/oem/vega/sysconfig/preferred-apps.xml — the piece that actually wins HOME"
<resources>
    <preferred-activities>
        <preferred-activity>
            <intent-filter>
                <action name="android.intent.action.MAIN" />
                <category name="android.intent.category.HOME" />
            </intent-filter>
            <component-name value="com.vega.launcher/.VegaLauncherActivity" />
        </preferred-activity>
    </preferred-activities>
</resources>
```

<Gotcha title="The stock Car Launcher has to be removed from the image, not just outranked">
Leaving both launchers installed with a `preferred-activity` pointed at
yours is fragile — a factory reset or a `pm clear` on the preference store
can drop back to the platform's default resolver, and with two HOME-capable
apps installed, that default is not guaranteed to be yours. Remove
`com.android.car.carlauncher` from `PRODUCT_PACKAGES` entirely, so there is
only ever one candidate for the role.
</Gotcha>

```makefile title="device/oem/vega/vega.mk"
# The replacement...
PRODUCT_PACKAGES += VegaLauncher

# ...and the stock one removed, not merely outranked
PRODUCT_PACKAGES -= CarLauncher
```

<Verify title="Verify only one HOME candidate exists">
```bash
m -j && adb shell reboot
adb wait-for-device
adb shell cmd package resolve-activity -a android.intent.action.MAIN \
  -c android.intent.category.HOME
```
The output should show exactly one activity: `com.vega.launcher/.VegaLauncherActivity`.
If `com.android.car.carlauncher` still appears, it was themed rather than
removed — go back to `PRODUCT_PACKAGES -=` and confirm the build actually
picked up the change (`adb shell pm list packages | grep carlauncher` should
return nothing).
</Verify>

## What replacing it actually costs

| | RRO theme | Full replacement |
| --- | --- | --- |
| Iteration | Seconds — push a new overlay APK | A full rebuild and reflash |
| Media widget, app-grid data source | Whatever Car Launcher's own logic does | Entirely your own implementation |
| CTS/VTS coverage | Inherited from the AOSP module | Your own responsibility, from scratch |
| Multi-display / occupant-zone launcher behaviour | Already handled | Reimplemented, and easy to get subtly wrong |
| Future AOSP Launcher improvements | Arrive automatically on a platform uprev | Do not arrive at all |

<Plain>
A themed Car Launcher gets every fix and feature the next AOSP uprev ships,
for free. A replacement gets none of them — every future improvement to
occupant-zone awareness, media session handling, or multi-display layout has
to be re-implemented, by you, forever. Replace it only when the actual
requirement is behavioural, not visual.
</Plain>

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| Theme did not apply | Resource not present in Car Launcher's own `overlayable.xml` — check before assuming the overlay path is wrong |
| Both launchers still resolve for HOME | Stock launcher only outranked, not removed from `PRODUCT_PACKAGES` |
| `resolve-activity` returns nothing | Manifest missing `CATEGORY_DEFAULT` alongside `CATEGORY_HOME` |
| Works after install, reverts after factory reset | Preference relied on `preferred-apps.xml` alone, with the stock launcher still present as a fallback candidate |

## What you have now

A themed stock launcher for the common case, and a working, correctly
exclusive replacement for the case that actually needs one — with the real
cost of the second path written down rather than discovered eighteen months
into owning a launcher fork.
