Adding one settings entry does not have to mean forking
`packages/apps/Car/Settings`. The module honors `EXTRA_SETTINGS` — the same
injection convention phone Settings has used for years — so an OEM app can
contribute a real, navigable settings screen from outside the module,
discovered at runtime from the activity's own manifest rather than compiled
in.

## How the injection point actually works

Car Settings queries every installed package for an **`Activity`** whose
`<intent-filter>` carries the action `com.android.settings.action.EXTRA_SETTINGS`,
then reads a handful of `<meta-data>` values declared directly on that same
activity — `com.android.settings.category`, `com.android.settings.title`,
and optionally `com.android.settings.icon` and `com.android.settings.summary`
— and adds one menu row per activity it finds this way.
`ExtraSettingsPreferenceController`, inside Car Settings itself, is what
does the pulling: it queries `PackageManager` for that action, reads the
metadata off each match, and drops a `Preference` into whichever
`LogicalPreferenceGroup` the category resolves to. Tapping the row starts
the activity the intent already resolved to — nothing is loaded in-process,
and nothing is fragment-hosted inside Settings' own navigation. There is no
`ContentProvider` anywhere in this mechanism, and no signature permission to
hold.

<Plain>
Car Settings is not asking "did anyone fork me." It is asking, at runtime,
"which installed activities advertise themselves as extra settings" — the
same question phone Settings has always asked for its own injected tiles.
Any app whose activity carries the right action and metadata gets a row,
without Settings' own source ever mentioning that app by name.
</Plain>

## Step 1 — Declare the activity and its metadata

```xml title="vendor/oem/vega/apps/VegaSettingsExtra/AndroidManifest.xml"
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    package="com.vega.settingsextra">

    <application>
        <activity
            android:name=".VegaDiagnosticsActivity"
            android:exported="true"
            android:label="@string/vega_diagnostics_title">

            <intent-filter>
                <action android:name="com.android.settings.action.EXTRA_SETTINGS" />
            </intent-filter>

            <meta-data
                android:name="com.android.settings.category"
                android:value="com.android.settings.category.vega_diagnostics" />
            <meta-data
                android:name="com.android.settings.title"
                android:value="@string/vega_diagnostics_title" />
            <meta-data
                android:name="com.android.settings.icon"
                android:resource="@drawable/ic_vega_diagnostics" />
            <meta-data
                android:name="com.android.settings.summary"
                android:resource="@string/vega_diagnostics_summary" />
        </activity>
    </application>
</manifest>
```

<Gotcha title="The action string is the entire contract — there is no permission backing it up">
Unlike the platform's signature permissions elsewhere in this series,
nothing gates this mechanism. `ExtraSettingsPreferenceController` finds the
row purely by matching the intent-filter action, byte for byte. A typo in
`com.android.settings.action.EXTRA_SETTINGS`, or metadata declared on a
component other than the one carrying that intent-filter, produces the same
result as not declaring it at all — no error, no log line, the row just
never appears.
</Gotcha>

## Step 2 — Provide the title, summary and icon it references

```xml title="vendor/oem/vega/apps/VegaSettingsExtra/res/values/strings.xml"
<resources>
    <string name="vega_diagnostics_title">Vega diagnostics</string>
    <string name="vega_diagnostics_summary">Live VHAL connection status and last sync time</string>
</resources>
```

<Gotcha title="title takes android:value, summary takes android:resource — they are not interchangeable">
`com.android.settings.title` is read through `android:value` (even though
the value itself is a `@string/…` reference); `com.android.settings.summary`
is read through `android:resource`. Swap the two and the failure is silent
rather than a build error — one field renders correctly and the other does
not, with nothing pointing at which meta-data element is wrong.
</Gotcha>

## Step 3 — Build the activity it points to

```java title="vendor/oem/vega/apps/VegaSettingsExtra/src/…/VegaDiagnosticsActivity.java (excerpt)"
public class VegaDiagnosticsActivity extends Activity {

    private Car mCar;

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        setContentView(R.layout.vega_diagnostics);

        // Car Service restarts on real hardware; use the lifecycle-listener
        // form so this activity never holds a manager past a disconnect.
        mCar = Car.createCar(this, /* handler= */ null,
                Car.CAR_WAIT_TIMEOUT_DO_NOT_WAIT, (car, ready) -> {
                    CarPropertyManager mgr = ready
                            ? (CarPropertyManager) car.getCarManager(Car.PROPERTY_SERVICE)
                            : null;
                    TextView status = findViewById(R.id.vhal_status);
                    status.setText(mgr != null ? "Connected" : "Unavailable");
                });
    }

    @Override
    protected void onDestroy() {
        mCar.disconnect();
        super.onDestroy();
    }
}
```

This is an ordinary `Activity` — it gets its own window and back stack, and
the driver sees a normal transition into and out of it, the same as tapping
into any other Settings screen contributed by a different app. That visible
transition, not a seamless in-process fragment swap, is what the real
`EXTRA_SETTINGS` mechanism buys you; no variant of this mechanism hosts
another app's UI in-process inside Car Settings' own navigation.

## Step 4 — Build, install, and confirm placement

```makefile title="device/oem/vega/vega.mk"
PRODUCT_PACKAGES += VegaSettingsExtra
```

```bash
m -j && adb install -r $ANDROID_PRODUCT_OUT/vendor/app/VegaSettingsExtra/VegaSettingsExtra.apk
```

<Verify title="Verify Car Settings actually discovered the activity">
```bash
# Confirm the activity actually advertises EXTRA_SETTINGS — this is the
# exact query ExtraSettingsPreferenceController itself runs
adb shell cmd package query-activities -a com.android.settings.action.EXTRA_SETTINGS | grep -i vega

# Open Settings and check where the row landed
adb shell am start -a android.settings.SETTINGS
```
Navigate to Settings on the emulator. "Vega diagnostics" should appear as a
row, without Car Settings having been rebuilt at all — confirm with `adb
shell dumpsys package com.android.car.settings | grep -i lastUpdateTime`,
which should still show the platform build's original timestamp, not
today's.
</Verify>

<Gotcha title="A category with nowhere to render it is a row query-activities finds and the UI never shows">
`query-activities` succeeding only proves the activity is discovered — it
does not prove the row is visible anywhere. `com.android.settings.category`
has to resolve to a `LogicalPreferenceGroup` that some screen in Car
Settings' own hierarchy actually declares and binds to
`ExtraSettingsPreferenceController`. Inventing a brand-new category string
does not create a new menu section for it — check `CategoryKey` and the
module's own preference XML for the group tied to the category you chose
before assuming the manifest wiring is the problem.
</Gotcha>

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| Row never appears, `query-activities` finds nothing | Intent-filter action does not exactly match `com.android.settings.action.EXTRA_SETTINGS` |
| Row appears, tapping it does nothing | Activity is not `android:exported="true"` |
| Row appears in the wrong place, or nowhere visible | Category value has no `LogicalPreferenceGroup` bound to it in Car Settings' hierarchy |
| Title shows as a raw resource string | `com.android.settings.title` given `android:resource` instead of `android:value` |
| Works after `adb install`, gone after reboot | APK not in `PRODUCT_PACKAGES` — the manually installed copy did not survive a fresh flash |

## What you have now

A settings screen a driver reaches through the platform's own Settings app,
contributed entirely from a separate, independently updatable package —
proof that most "we need to fork Settings" requirements are actually this
injection point, not yet discovered.
