`android.hardware.automotive.occupant_awareness` is architecturally distinct
from EVS: EVS streams raw exterior camera frames to an app, while occupant
awareness is a *detection-result* HAL — whatever's watching the cabin
reports structured driver-state events like gaze direction and distraction
level, never pixels. AOSP ships a real mock implementation of it, and a real
waiting consumer in CarService — but bringing the two together for the first
time on a product means clearing three separate gates, each of which fails
with a message that looks nothing like the others.

## Step 0 — Confirm it's genuinely not wired up

```bash
adb shell service list | grep -i occupant
# (nothing)
```

<FileTree>
hardware/interfaces/automotive/occupant_awareness/aidl/mock/
├── Android.bp                          # missing init_rc + vintf_fragments
├── service.cpp
├── OccupantAwareness.cpp

The mock binary exists in source; it's simply missing the two properties
that turn a plain binary into a real, init-managed Treble service:

```json title="Android.bp — add these to the existing cc_binary"
init_rc: ["occupant_awareness_mock.rc"],
vintf_fragments: ["occupant_awareness_mock-service.xml"],
```

```text title="occupant_awareness_mock.rc"
service hal_occupant_awareness_default /vendor/bin/hw/android.hardware.automotive.occupant_awareness@1.0-service_mock
    class hal
    user system
    group system
```

## Gate 1 — A build-system inheritance mechanism, not a real policy error

```text
init: Could not start service 'hal_occupant_awareness_default' ...
  File ...-service_mock (labeled "u:object_r:vendor_file:s0") has incorrect label
  or no domain transition from u:r:init:s0 to another SELinux domain defined.
```

<Gotcha title="Two mechanisms both claim to add vendor sepolicy — only one actually compiles it">
The upstream product template for this HAL wires its policy through
`PRODUCT_PRIVATE_SEPOLICY_DIRS`/`PRODUCT_PUBLIC_SEPOLICY_DIRS`. Confirmed by
pulling the compiled policy off the device: the service binary's label
never appears in `/vendor/etc/selinux/vendor_file_contexts` at all.
`BOARD_SEPOLICY_DIRS` is the mechanism that actually reaches vendor-side
policy for a product built this way.
</Gotcha>

```makefile title="Fix"
BOARD_SEPOLICY_DIRS += packages/services/Car/car_product/occupant_awareness/sepolicy
```

```text title="The HAL itself now starts clean"
init: starting service 'hal_occupant_awareness_default'...
...-service_mock: Service default is ready
servicemanager: Found .../IOccupantAwareness/default in device VINTF manifest.
```

CarService still doesn't want it:

```text
ICarImpl: Skip initializing service for class: OccupantAwarenessService
because feature: occupant_awareness is disabled
```

## Gate 2 — An overlayable with a real name

Enabling an optional CarService feature is a resource,
`config_allowed_optional_car_features`, using the same overlay mechanism
covered in the RRO tutorial — but this target genuinely declares a named
`<overlayable>`, and demands the overlay match it exactly:

```text
idmap2d: overlay '.../OccupantAwarenessRRO.apk' is not allowed to overlay
  resource 'array/config_allowed_optional_car_features' in target:
  <overlay> android:targetName "" does not match overlayable name "CarServiceCustomization"
```

<Gotcha title="An empty targetName only works when there's nothing to match">
Some overlay targets have no `<overlayable>` declaration at all and fall
back to a default policy where an unnamed overlay works. CarService's own
resources are explicitly, individually overlayable, and an overlay missing
the matching `android:targetName` is rejected outright rather than silently
falling back.
</Gotcha>

```xml title="Fix"
<overlay android:targetPackage="com.android.car.updatable"
         android:targetName="CarServiceCustomization"
         android:isStatic="true" android:priority="1" />
```

```text
CarFeatureController: Loaded default features:{..., occupant_awareness, ...}
CAR.OccupantAwarenessService: Failed to find OAS hal_service at: [.../IOccupantAwareness/default]
SELinux: avc: denied { find } ... scontext=u:r:carservice_app:s0 tcontext=u:object_r:hal_occupant_awareness_service:s0
```

## Gate 3 — An attribute nobody ever assigned

The deepest gate: the upstream sepolicy package defines
`hal_occupant_awareness_client` as a real attribute and grants it `find`
permission on the service — but never assigns that attribute to any actual
domain anywhere in the tree. It was written to be consumable, and never
actually consumed.

```text title="carservice_app is the one real, in-tree client — spell out the association"
typeattribute carservice_app hal_occupant_awareness_client;
```

<Verify title="Verify the connection">
```bash
adb shell dumpsys car_service --services OccupantAwarenessService
# *OccupantAwarenessService*
# Connected to HAL service
# 0 change listeners subscribed.
```
Three real, independent gates — a build-system inheritance mechanism, a
named overlay policy, and a sepolicy attribute assignment nobody had ever
needed before — cleared one at a time, each pointing precisely at its own
fix.
</Verify>

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| Service file has an "incorrect label" at boot | Vendor sepolicy declared via `PRODUCT_*_SEPOLICY_DIRS` instead of `BOARD_SEPOLICY_DIRS` — the latter is what actually compiles for this build type |
| "Skip initializing service... feature disabled" | The optional feature isn't in `config_allowed_optional_car_features` yet |
| Overlay rejected with a `targetName` mismatch | The target has a named `<overlayable>` — match it exactly, don't leave it blank |
| `avc: denied { find }` on the service, after the feature is enabled | The client domain was never assigned the HAL's own client attribute — add the `typeattribute` line |

## Confirming real data actually flows

A successful connection only proves the wiring — process discovery,
sepolicy, the AIDL handshake. It says nothing about whether a real
detection event, carrying real occupant and gaze data, actually reaches an
app's own callback. The mock HAL's `DetectionGenerator` produces a genuine,
if deliberately fixed rather than randomized, test payload:

```cpp title="hardware/interfaces/automotive/occupant_awareness/aidl/mock/DetectionGenerator.cpp"
presenceDetection.isOccupantDetected = true;
// role == DRIVER:
driverMonitoringDetection.confidenceScore = ConfidenceLevel::HIGH;
driverMonitoringDetection.isLookingOnRoad = 0;
```

<Verify title="Register a listener and watch real events arrive">
```java
int capability = oaManager.getCapabilityForRole(VEHICLE_OCCUPANT_DRIVER);
oaManager.registerChangeCallback(callback);
```
```bash
# driver capability flags: 5  (presence + driver-monitoring, as bits)
# onDetectionEvent: role=2, isPresent=true, driverMonitoringDetection=(null)
# onDetectionEvent: role=4, isPresent=true,
#   driverMonitoringDetection=DriverMonitoringDetection{confidenceLevel=2,
#     isLookingOnRoad=false, gazeDurationMillis=28316}
```
`role=2`/`role=4` match `VEHICLE_OCCUPANT_FRONT_PASSENGER`/`_DRIVER`'s real
bit values (`1<<1`, `1<<2`) — events are correctly separated by occupant
role, with the structured `DriverMonitoringDetection` payload present only
on the driver-role event, exactly as it should be for a detection type that
only makes sense for the driver's seat. `isLookingOnRoad=false` matches the
generator's hardcoded source value exactly, confirming the data arrives
unmodified through the entire stack rather than being stray or corrupted.
Force-stopping the listening app drops the service's own subscriber count
back to zero immediately, while the underlying HAL connection stays up,
untouched by one client coming and going.
</Verify>
