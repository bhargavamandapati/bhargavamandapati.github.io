Vehicle Map Service exists to share map and traffic data between apps that
shouldn't have to know about each other — a navigation app publishes a
"layer," and anything interested subscribes to it, with the broker
handling discovery and routing. It's a real, complete pub/sub system, and it
runs whether or not any product ships a publisher for it.

## Step 1 — Know which API generation you're reading

`car-lib` ships two ways to talk to VMS, and the source is explicit about
which one is current:

```java title="VmsSubscriberManager.java"
/**
 * @deprecated Use {@link VmsClientManager} instead.
 */
@Deprecated
@SystemApi
public final class VmsSubscriberManager extends CarManagerBase { ... }
```

`VmsPublisherClientService` carries the identical notice. Both are real,
working compatibility wrappers — `VmsSubscriberManager.wrap()` literally
builds one from a live `VmsClientManager` — but the current, undecorated API
is `VmsClientManager`/`VmsClient`.

<Gotcha title="Dump the broker, not the client manager">
`VmsClientManager` has no dump output of its own. The routing state — every
provider's offerings, every subscriber's subscriptions — lives in
`VmsBrokerService`:
```bash
adb shell dumpsys car_service --services VmsBrokerService
```
</Gotcha>

## Step 2 — Register as a provider, and subscribe to your own layer

A single app can legitimately be both halves at once — its own provider and
its own subscriber of one layer, which is the cleanest way to prove the
plumbing works before writing a second app.

```java title="A minimal probe"
public void onClientConnected(VmsClient client) {
    int providerId = client.registerProvider("tutorial-probe".getBytes(UTF_8));
    client.setProviderOfferings(providerId, Set.of(new VmsLayerDependency(LAYER)));
    client.setSubscriptions(Set.of(new VmsAssociatedLayer(LAYER, Set.of(providerId))));
    client.publishPacket(providerId, LAYER, PAYLOAD);
}
```

<Gotcha title="A distraction-optimized check applies here too">
An activity with no `distractionOptimized` metadata can be blocked outright
while the vehicle isn't parked — the exact UXR gate covered in the driver
distraction tutorial. If your first attempt is silently blocked with "You
can't use this feature while driving," check the driving state before
suspecting VMS itself.
</Gotcha>

<Verify title="Verify the round trip end to end">
```bash
adb logcat -d | grep VmsLoopbackProbe
# onClientConnected
# registerProvider() -> providerId=1
# offered + subscribed to layer VmsLayer { type = 12345, channel = 0, version = 1 }
# onLayerAvailabilityChanged: ... providerIds = {1}
# onSubscriptionStateChanged: ... providerIds = {1}
# onPacketReceived providerId=1 layer=VmsLayer {...} text="hello" matchesSentPayload=true
```
Every stage fires in order: the provider registers, the offering and
subscription both come back as real availability/subscription-state change
events (not accepted silently), and the exact payload published arrives back
through `onPacketReceived`, byte for byte.
</Verify>

```bash title="Confirmed from the server side, the same moment"
adb shell dumpsys car_service --services VmsBrokerService
# mClientMap:
#   VmsClient [com.example.vmsprobe]
#     Offerings:      Provider [1]  VmsLayer { type = 12345, ... }
#     Subscriptions:  VmsLayer { type = 12345, ... }: {1}
```

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| Broker dump shows empty `mAvailableLayers`/`mClientMap` | Expected until at least one client registers — the routing logic isn't a stub, it's just unused until something calls in |
| Request silently blocked | Check driving state and `distractionOptimized` metadata — a UXR restriction, not a VMS problem |
| No dump output for `VmsClientManager` | Dump `VmsBrokerService` instead — it's the one with real state |
| Using `VmsSubscriberManager` and seeing a deprecation warning | Expected — migrate to `VmsClientManager` for new code |
