The CAN HAL tutorial ended on an honest gap: a correctly decoded frame, a
`HW_KEY_INPUT` property write that looked right — and zero key events
dispatched. This picks that thread back up, turns on a debug flag AOSP
already ships for exactly this situation, and finds the actual cause: one
field, set to the wrong value, in reference sample code.

## Where the last tutorial left off

A hand-built injection tool sent a real, bit-packed frame onto the virtual
bus. The reference consumer decoded it correctly — `EncPos: 0`, `EncDir: 0`,
`Buttons: 1` — and built a `HW_KEY_INPUT` property value to match.
`CarInputService` had confirmed at boot that it supports key input and
subscribed. And yet:

```bash
adb shell dumpsys car_service --services CarInputService | tail -1
# mNumKeyEventsDispatched:0,mNumRotaryEventsDispatched:0
```

Zero. The property write itself was silent — no error, no confirmation —
because the fake VHAL implementation's write path has no log line on that
branch. The only way to see further in is to turn one on.

## Step 1 — A debug flag AOSP already wired for this

```cpp title="hardware/interfaces/automotive/vehicle/aidl/impl/current/fake_impl/hardware/src/FakeVehicleHardware.cpp"
#define FAKE_VEHICLEHARDWARE_DEBUG false  // STOPSHIP if true.
```

One line, guarding exactly the log statement that would explain a silent
drop — inside the function that decides whether an updated property value
actually reaches a subscriber:

```cpp
void FakeVehicleHardware::onValuesChangeCallback(std::vector<VehiclePropValue> values) {
    for (const auto& value : values) {
        PropIdAreaId propIdAreaId{.propId = value.prop, .areaId = value.areaId};
        if (mRefreshInfoByPropIdAreaId.find(propIdAreaId) == mRefreshInfoByPropIdAreaId.end() &&
            mSubOnChangePropIdAreaIds.find(propIdAreaId) == mSubOnChangePropIdAreaIds.end()) {
            if (FAKE_VEHICLEHARDWARE_DEBUG) {
                ALOGD("The updated property value: %s is not subscribed, ignore", ...);
            }
            continue;
        }
        subscribedUpdatedValues.push_back(value);
    }
    (*mOnPropertyChangeCallback)(std::move(subscribedUpdatedValues));
}
```

<Gotcha title="The filter key is a pair, not a property alone">
Everything is matched as a `{propId, areaId}` pair against
`mSubOnChangePropIdAreaIds`, which is populated by real subscribe calls from
the framework — not just by a property being present in config. Get the
`areaId` half wrong and the match fails even though the property itself is
correct and subscribed.
</Gotcha>

Flip the flag — this is a local debug build, never shipped, and the comment
says so directly — and rebuild:

```cpp
#define FAKE_VEHICLEHARDWARE_DEBUG true  // STOPSHIP if true.
```

## Step 2 — The real line, caught live

```bash title="Same frame as before, fresh boot"
adb shell /data/local/tmp/caninject vcan0 18a 0000000100

# FakeVehicleHardware: The updated property value: VehiclePropValue{
#   timestamp: 36195071820, areaId: 16777216,
#   prop: 289475088, status: AVAILABLE,
#   value: RawPropValues{int32Values: [0, 96, 0], ...}} is not subscribed, ignore
```

`prop: 289475088` is `HW_KEY_INPUT` (confirm with
`dumpsys android.hardware.automotive.vehicle.IVehicle/default --list`).
`int32Values: [0, 96, 0]` is exactly
`[ACTION_DOWN, AKEYCODE_BUTTON_A, VehicleDisplay::MAIN]` — the decode was
perfect. The only thing wrong is `areaId: 16777216`.

## Step 3 — The one-field bug

```cpp title="A reference decoder, real AOSP sample code"
prop.areaId = toInt(VehicleArea::GLOBAL);
```

The AIDL definition names the exact mistake in its own doc comment, right
next to the enum being misused:

```aidl title="VehicleArea.aidl"
* properties must be of the VehicleArea#GLOBAL area type.
* ...
* however, the area ID must be 0.
GLOBAL = 0x01000000,
```

<Gotcha title="A type tag is not a value">
`VehicleArea::GLOBAL` is `0x01000000` = `16777216` — a type tag used when
*declaring* which area class a property belongs to. It is explicitly, in
writing, not a valid value for `VehiclePropValue.areaId` on a global
property; that field must be the literal integer `0`. Reference sample code
used the enum where the convention calls for a bare zero.
`CarInputService` subscribed correctly at `areaId=0`; every event this
function emitted arrived at `areaId=16777216` instead, and was silently
dropped by an exact-match filter that had no reason to suspect the two were
meant to be the same thing.
</Gotcha>

## Step 4 — Fix it, and prove it live

```diff
-    prop.areaId = toInt(VehicleArea::GLOBAL);
+    // A GLOBAL-area property's VehiclePropValue.areaId must be 0, not
+    // VehicleArea::GLOBAL's own enum value (0x01000000) — see the areaId
+    // doc comment on VehicleArea.aidl.
+    prop.areaId = 0;
```

```bash title="Rebuild, relaunch, same frame"
adb shell /data/local/tmp/caninject vcan0 18a 0000000100
adb shell dumpsys car_service --services CarInputService | tail -1
# mNumKeyEventsDispatched:0,mNumRotaryEventsDispatched:0
```

Still zero — but this time there's no `FakeVehicleHardware` log line at all,
not even a rejection.

<Gotcha title="Silence can mean the fix worked">
The only `ALOGD` on that path fires on the *rejected* branch. No log means
the value cleared the filter and was handed on to the real callback.
`mNumKeyEventsDispatched` turns out to be measuring something else entirely —
it lives in `InputCaptureClientController`, and only increments for input
routed through the explicit capture-client API, which a plain button press
doesn't use. It was the wrong instrument for this test, not a sign the fix
failed.
</Gotcha>

<Verify title="Verify with the instrument that's actually measuring this">
```bash
# SystemUI's own rotary/key listener logs every event it actually receives —
# check that instead of the capture-client counter.
adb shell /data/local/tmp/caninject vcan0 18a 0000000100
# RotaryController: onAccessibilityEvent: EventType: TYPE_VIEW_FOCUSED

# A precisely countable second test: an encoder-position delta of exactly 3
# should produce exactly three DPAD_DOWN down/up pairs.
adb shell /data/local/tmp/caninject vcan0 18a 0300000000
# RotaryController: onKeyEvents KeyEvent { action=ACTION_DOWN, keyCode=KEYCODE_DPAD_DOWN }
# RotaryController: onKeyEvents KeyEvent { action=ACTION_UP,   keyCode=KEYCODE_DPAD_DOWN }
# RotaryController: onKeyEvents KeyEvent { action=ACTION_DOWN, keyCode=KEYCODE_DPAD_DOWN }
# RotaryController: onKeyEvents KeyEvent { action=ACTION_UP,   keyCode=KEYCODE_DPAD_DOWN }
# RotaryController: onKeyEvents KeyEvent { action=ACTION_DOWN, keyCode=KEYCODE_DPAD_DOWN }
# RotaryController: onKeyEvents KeyEvent { action=ACTION_UP,   keyCode=KEYCODE_DPAD_DOWN }
```
An encoder delta of exactly 3, encoded into one CAN frame, produced exactly
three down/up pairs — six real Android `KeyEvent` objects, with the right key
code and the right count. One field, changed from an enum's own value to a
literal zero, is the entire difference between a frame that vanishes without
a trace and one that drives real framework key events end to end.
</Verify>

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| A property write logs nothing at all | `FAKE_VEHICLEHARDWARE_DEBUG` is off by default — flip it for a local debug build |
| Log says "is not subscribed, ignore" despite a real subscriber | Check the `areaId` half of the pair, not just the property ID |
| `mNumKeyEventsDispatched` stays 0 after a fix that worked | That counter only tracks the input-capture-client API — check SystemUI's own listener instead |
| A global property's value never matches a subscription | Its `areaId` must be the literal `0`, never `VehicleArea::GLOBAL`'s own enum value |
